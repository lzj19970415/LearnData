07 备份恢复与数据库安全（运维岗的加分题）

一、人话开场：备份是"快照+流水账"，安全是"分清谁能干什么"

把数据库想成一家银行：

  • 备份 = 定期给金库拍一张快照（完全备份），再配一本流水账（binlog 日志）。哪天金库塌了：先按最近一张快照把家底复原，再照着流水账把"快照之后发生的每一笔"补回来——一毛钱不差。
  • 安全 = 分清"谁能干什么"：柜员只能办自己柜台的业务（权限控制）、实习生看不到工资那一列（视图遮挡）、金库每扇门的刷卡记录都留着（审计），出了事能追到人。

一句话总结：备份解决"坏了怎么办"，安全解决"谁能进来、能干到哪一步"。 你有运维背景，这一章就是主场——上午概念题直接送分，下午运维类简答题也最爱从这里出。

二、⚠️【必考】三种备份方式：完全 / 差异 / 增量

备份方式人话含义备份内容备份量恢复所需文件恢复速度
完全备份给全部数据重拍一张完整快照全部数据最大仅 1 份完全备份最快，一步到位
差异备份只补拍"相对最近一次快照"的变化上次完全备份以来变化的数据逐日增大最近 1 次完全备份 + 最近 1 次差异备份较快，只需 2 份
增量备份只记"相对上次任何一次备份"的变化上次任意备份（完全或增量）以来变化的数据最小最近完全备份 + 之后全部增量备份（按时间顺序重放）最慢，份数多且不能乱序

口诀：备份量：全 > 差 > 增；恢复速度：全 > 差 > 增；备份速度：增 > 差 > 全——备份省事的恢复就费事，二者不可兼得。

❗【易错】两处最容易掉坑：

  • 差异备份的参照物永远是上一次完全备份，不是上一次差异备份！
  • 增量备份的参照物是上一次任意备份（完全备份或增量备份都算）。

场景推演：周日 0 点做完全备份，周一至周三每天各做一次备份，周四中午库坏了。

  • 若每天做差异备份：恢复 = 周日完全备份 + 周三差异备份，两份搞定。
  • 若每天做增量备份：恢复 = 周日完全备份 + 周一 + 周二 + 周三增量备份，缺一不可、顺序不能乱。

三、热备 / 温备 / 冷备（按备份时数据库的状态分）

方式备份时数据库状态对业务影响人话
热备份（Hot Backup）正常对外服务，读写均不受影响零影响营业中拍照
温备份（Warm Backup）只能读、不能写查询正常，写入被阻塞只许看不许动
冷备份（Cold Backup）数据库正常关闭后备份需要停机下班锁门后拍照
  • 7×24 小时业务只能选热备；冷备最安全（没人动数据）但必须停机——上午选择题常拿这对矛盾设问；InnoDB 支持热备，MyISAM 不支持事务，通常只能温备或冷备。

四、⚠️【必考】MySQL 两大备份工具：mysqldump vs XtraBackup

对比项mysqldump（逻辑备份）XtraBackup（物理备份）
备份原理把库和表导成一堆 CREATE / INSERT SQL 语句直接拷贝数据文件（.ibd）和日志文件
人话类比把账本重新抄成一份"建库说明书"把整个仓库连货架一起打包搬走
备份/恢复速度慢（要生成 SQL、恢复时要逐条重放）快（文件级复制，不经过 SQL 解释执行）
备份文件形态文本 .sql，人能读、可改、跨版本跨平台二进制数据文件，与版本/引擎强绑定
适合库规模中小库（GB 级以内）大库（TB 级）
热备支持加 --single-transaction 可对 InnoDB 做一致性快照备份原生支持 InnoDB 热备
增量备份不直接支持支持
出品方MySQL 自带Percona（社区免费）

常用命令（要求会写会认）：

# 逻辑备份：备份单个库（--single-transaction 保证 InnoDB 备份期间数据一致）
mysqldump -uroot -p --single-transaction mydb > /backup/mydb_20261028.sql
# 恢复方式一：登录 mysql 后用 source
mysql -uroot -p
mysql> source /backup/mydb_20261028.sql;

# 恢复方式二：在操作系统上直接重定向导入
mysql -uroot -p mydb < /backup/mydb_20261028.sql

五、⚠️【MySQL高频】binlog：二进制日志

binlog 是 MySQL Server 层的日志，记录所有会改变数据的操作（DDL 语句 + DML 语句事件），不记录 SELECT / SHOW 等只读操作。

作用说明
主从复制从库拉取并重放主库 binlog，保持与主库一致（08 篇详讲）
时间点恢复配合完全备份，把库恢复到过去的任意时刻（Point-in-Time Recovery）

人话：完全备份是"快照照片"，binlog 是"快照之后的流水账"。快照 + 流水账 = 还原任意时刻。

5.1 "完全备份 + binlog"恢复到任意时间点（运维场景题模板）

场景：周三凌晨 2 点做了完全备份，周四上午 10:05 有人误执行 DROP TABLE，要恢复到误删前一秒。

第1步：停止业务写入（或先备份当前 binlog），锁住现场
        ↓
第2步：用最近一次完全备份，把库还原到周三凌晨 2 点
        ↓
第3步：用 mysqlbinlog 定位误删语句的位置（时间点或 pos 位点）
        ↓
第4步：重放"完全备份之后 → 误删之前"这一段 binlog
        ↓
第5步：数据回到误删前一秒，恢复业务
# 把 binlog 翻译成可读 SQL，肉眼定位 DROP TABLE 所在位点
mysqlbinlog --no-defaults mysql-bin.000003 > /tmp/bin_log.sql

# 只重放到误删时刻之前（--stop-position 按 pos 位点同理）
mysqlbinlog mysql-bin.000003 \
  --start-datetime="2026-10-29 02:00:00" \
  --stop-datetime="2026-10-30 10:05:00" | mysql -uroot -p

❗【易错】--stop-datetime 指定的时刻本身不会被重放（到点即停），填误删时刻 10:05 正好截在事故之前；恢复操作前必须先备份当前 binlog，防止"边恢复边写入"把现场搞乱。

六、⚠️【上午必考】数据库安全四大机制

教材连击顺序：DAC 自主存取控制 → MAC 强制存取控制 → 视图 → 审计。

6.1 自主存取控制（DAC）

  • 全称：Discretionary Access Control，自主存取控制。
  • 特点：用户对自己创建的对象拥有自主授权的权力——可以把权限授予别人、随时收回，甚至允许对方继续转授（WITH GRANT OPTION），"自主"二字就体现在这。
  • SQL 实现：GRANT / REVOKE。
  • 模型表示：存取权限矩阵——行是用户（主体），列是表/视图（客体），格子里填允许的操作（SELECT、INSERT、UPDATE…）。

人话：你家的钥匙你说了算，想配几把、借给谁，你自己定。

GRANT SELECT, INSERT ON TABLE emp TO 'zhangsan'@'localhost';
REVOKE INSERT ON TABLE emp FROM 'zhangsan'@'localhost';

6.2 强制存取控制（MAC）

  • 全称：Mandatory Access Control，强制存取控制。
  • 特点：给每个主体（用户、进程）和客体（表、视图、行）都贴上安全级别标签，由系统按级别强制判定能否读写——连数据拥有者自己都改不了规则。
  • 安全级别从高到低：绝密 TS > 机密 S > 秘密 C > 公开 I。
操作铁律人话解释
读（Read）主体许可级别 ≥ 客体级别，才能读只能向下读，不许偷看比自己级别高的数据
写（Write）主体级别 ≤ 客体级别，才能写只能向上写，防止把机密内容写进低级别客体造成泄露

⚠️【必考】口诀："读下写上"。想通泄密路径就忘不了：低级别的人若能"读上"，就偷看了机密；若能"写下"，就能把机密内容搬运到低级别文件里公开——两条路全被堵死。

6.3 DAC vs MAC 对比表【必考】

对比项DAC 自主存取控制MAC 强制存取控制
谁说了算对象拥有者自主授权系统按安全级别强制判定
授权方式GRANT / REVOKE，可转授预先标定主体/客体级别，用户不可改
灵活性灵活、效率高严格、缺乏灵活性
安全强度较弱，权限可能被随意扩散强，杜绝越级读写
理论模型存取权限矩阵BLP 模型，"读下写上"
典型应用一般商用数据库（MySQL 权限体系）军事、政府等高保密系统

6.4 视图机制

  • 视图（View）是虚拟表：本身不存数据，只存一条查询语句。
  • 安全用途：把敏感行/敏感列藏起来——只给用户开视图权限、不开底表权限，被隐藏的部分他天然看不到。
  • 附加好处：简化查询、提供逻辑独立性。
-- 员工表 emp 含工资列，给实习生只开"不含工资"的视图
CREATE VIEW emp_public AS SELECT emp_id, emp_name, dept FROM emp;
GRANT SELECT ON emp_public TO 'trainee'@'%';   -- 只授权视图，不给原表

6.5 审计（Audit）

  • 定义：由 DBMS 自动记录"谁（用户）、何时、对哪个对象、执行了什么操作、结果如何"的日志机制。
  • 作用：事后追责、安全威慑、发现异常。注意审计不能事前阻止违规，它是 DAC / MAC 的补充手段——"补充"二字是选择题高频坑点。
  • 教材语句：AUDIT 设置审计、NOAUDIT 取消审计；MySQL 用企业版审计插件实现同类功能，考试按教材概念作答即可。

四大机制一句话串记：DAC 管授权，MAC 管级别，视图管遮挡，审计管追责。

七、⚠️【必考名词解释】数据完整性三类

下午案例题常直接考"XX 完整性"名词解释，下表"标准定义"列一字不差背下来：

完整性类别标准定义（背这句）SQL 实现
实体完整性规定基本表的主键不能取空值且必须唯一，用于唯一标识表中的每一个实体PRIMARY KEY
参照完整性规定外键的取值要么为空，要么必须等于被参照表中某条记录的主键值FOREIGN KEY ... REFERENCES ...
用户自定义完整性针对具体应用环境，由用户自行定义的数据约束条件CHECK、NOT NULL、UNIQUE、DEFAULT

人话对照：

  • 实体完整性 → 身份证号不能为空、不能重号，每行必须有"身份"。
  • 参照完整性 → 填"所属部门"时只能填部门表里真实存在的部门（或干脆不填），不能瞎编一个不存在的部门。
  • 用户自定义 → 公司自家定的规矩，如"工资不得低于 2000"。
CREATE TABLE emp (
    emp_id  INT PRIMARY KEY,                        -- ① 实体完整性
    dept_id INT,
    name    VARCHAR(50) NOT NULL,                   -- ② 用户自定义完整性
    phone   VARCHAR(20) UNIQUE,                     -- ② 用户自定义完整性
    salary  DECIMAL(10,2) CHECK (salary >= 2000),   -- ② 用户自定义完整性
    CONSTRAINT fk_dept FOREIGN KEY (dept_id)
        REFERENCES dept(dept_id)                    -- ③ 参照完整性
);

❗【易错】NOT NULL 和 UNIQUE 在教材分类里属于用户自定义完整性，不是实体完整性——选择题专门拿这个挖坑。判定技巧：凡是"具体业务规定的规则"（取值范围、默认值、非空）都归用户自定义。

八、触发器

  • 定义：触发器（Trigger）是用户定义在表上、由 INSERT / UPDATE / DELETE 等事件自动触发执行的特殊存储过程——不能带参数、不能被显式调用。
  • 两大作用（背这两条就够了）：
    1. 强制执行比 CHECK 更复杂的约束规则（跨表、跨行、需要查询其他数据的业务规则）；
    2. 审计：自动记录变更痕迹（谁、何时、改了什么）。
-- 例：禁止非工作时间修改工资（CHECK 做不到"看时间"，触发器能）
CREATE TRIGGER trg_salary_guard
BEFORE UPDATE ON emp
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary AND HOUR(NOW()) NOT BETWEEN 9 AND 18 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '非工作时间禁止修改工资';
    END IF;
END;

九、SQL 注入：原理与防范【运维岗高频】

9.1 原理：把"数据"喂成了"代码"

程序把用户输入直接拼进 SQL 字符串，攻击者输入的内容里夹带 SQL 命令，随整条语句一起被执行：

-- 程序里拼接写法（错误示范）：
sql = "SELECT * FROM users WHERE uname='" + uname + "' AND pwd='" + pwd + "'";
-- 攻击者在用户名框输入： admin' --
-- 拼出来的语句实际变成：
SELECT * FROM users WHERE uname='admin' --' AND pwd='';
-- "--" 把后半段密码判断注释掉了，不知道密码也能以 admin 身份登录！

9.2 典型危害

危害表现
绕过登录万能密码 admin' -- 直接进后台
拖库构造注入语句批量导出全库数据
篡改/破坏数据追加 ; DROP TABLE ...
摸清库结构借报错信息或盲注，一步步猜出库名、表名、字段

9.3 防范清单【必背】

手段说明地位
预编译 / 参数化查询SQL 结构先定死，用户输入只往占位符 ? 里填，永远只是数据、不会变代码⚠️ 最根本、治本
最小权限原则应用连接账号只授必要权限，不给 DROP / FILE / SUPER保底止损
输入校验白名单校验类型、长度、格式前置过滤
屏蔽报错信息不把数据库原始报错返回给用户（报错是注入的情报来源）减少情报
定期审计 + WAF审计日志配合 Web 应用防火墙，发现异常 SQL 及时告警事后兜底

口诀：参数化治本，最小权限保底，校验屏蔽减风险，审计 WAF 兜住底。

十、用户与权限管理

-- 创建用户（格式：'用户名'@'来源主机' IDENTIFIED BY '密码'）
CREATE USER 'backup'@'192.168.1.%' IDENTIFIED BY 'Back#2026';

-- 授权：按最小权限原则，备份账号只给 SELECT + 锁表
GRANT SELECT, LOCK TABLES ON *.* TO 'backup'@'192.168.1.%';

-- 查看用户权限
SHOW GRANTS FOR 'backup'@'192.168.1.%';

-- 收回权限 / 删除用户
REVOKE LOCK TABLES ON *.* FROM 'backup'@'192.168.1.%';
DROP USER 'backup'@'192.168.1.%';
  • MySQL 的用户身份是"用户名 + 来源主机"两维的：'backup'@'192.168.1.%' 和 'backup'@'%' 是两个不同的用户。
  • ⚠️ 最小权限原则（Least Privilege）：只授予完成本职工作所必需的权限，多余的一律不给，需要时再申请。备份不用 root、应用账号不给 DDL——这是运维岗位的基本素养，也是案例题的采分点。

十二、自测 5 题（改编自历年真题风格）

1. 某系统每周日 0 点做完全备份，周一至周三每天只备份"自最近一次完全备份以来发生变化的数据"。周四中午数据库损坏，正确的恢复方案是（　）。

A. 周日完全备份 → 周一备份 → 周二备份 → 周三备份，依次恢复 B. 周日完全备份 → 周三备份，两步恢复 C. 仅恢复周三备份即可 D. 周日完全备份 → 周三备份 → 周一备份 → 周二备份

答案：B。题干"自最近一次完全备份以来变化的数据"是差异备份的定义，恢复只需"最近一次完全备份 + 最近一次差异备份"两份。A 是增量备份的恢复方式；C 缺少完全备份；D 顺序错误。

2. 采用强制存取控制的系统中，主体许可级别为 S（机密），客体级别为 C（秘密），则主体对该客体（　）。

A. 可以读，不可以写 B. 可以写，不可以读 C. 既可读又可写 D. 既不可读又不可写

答案：A。读规则"主体许可级别 ≥ 客体级别"：S ≥ C 成立，可读；写规则"主体级别 ≤ 客体级别"：S > C 不成立，不可写。即"读下写上"——机密级用户能看秘密级文件，但不能往秘密级客体写内容（防止机密内容降级泄露）。

3. 银行系统规定"贷款金额必须大于 0 且不超过 100 万元"，该约束属于（　）。

A. 实体完整性 B. 参照完整性 C. 用户自定义完整性 D. 强制存取控制

答案：C。这是具体应用环境下的取值约束，由用户自行定义、用 CHECK 实现，属于用户自定义完整性。实体完整性管主键非空唯一，参照完整性管外键取值，均与取值范围无关。

4. 防范 SQL 注入最根本的手段是（　）。

A. 对用户输入限制最大长度 B. 使用预编译语句（参数化查询） C. 屏蔽数据库的报错信息 D. 定期修改数据库账号密码

答案：B。预编译先固定 SQL 结构，用户输入只作为数据填充占位符，从原理上杜绝"输入变代码"。A、C 只是辅助手段；D 无关——注入者用的正是合法账号，改密码防不住。

5. 关于 MySQL 的 binlog，下列说法错误的是（　）。

A. 记录 DDL 语句和 DML 操作事件 B. 是主从复制功能的基础 C. 可用于将数据库恢复到指定时间点 D. 记录所有 SELECT 查询语句

答案：D。binlog 只记录会改变数据的操作（DDL + DML），SELECT / SHOW 等只读操作不记录。A、B、C 恰是它的记录内容和两大作用，全部正确。
