02 数据模型与ER图（案例题第一大件的根基）

一、人话开场：ER图=先不关心里怎么存，只画「有什么人、什么东西、什么关系」

给一个学校做管理系统，新手第一反应是"建几张表、用什么类型、加什么索引"——错，这是把最后一步当第一步。

正确的顺序是先回答三个"幼儿园问题"：

  1. 系统里有哪些"人"和"东西"？——学生、课程、老师（这是实体）
  2. 每个"人/东西"有哪些特征？——学生有学号、姓名、生日（这是属性）
  3. 它们之间什么关系？——学生"选修"课程（这是联系）

把这三个问题的答案画成一张图，就是 ER 图（实体联系图）。它故意不关心物理存储（那是内模式的事），只面向业务、面向用户沟通——还记得 01 篇说的吗？ER 是概念模型，与具体 DBMS 无关。

一句话总纲：先画有什么、再画什么关系、最后才谈怎么存。

二、三大基本构件：实体、属性、码

2.1 定义对照表

构件正式定义人话ER符号
实体（Entity）客观存在并可相互区别的事物一个个"人/东西"矩形
属性（Attribute）实体所具有的某一特性事物的特征椭圆
码/键（Key）唯一标识一个实体的属性（集）一行的"身份证"椭圆下加下划线
联系（Relationship）实体之间的相互关联谁和谁怎么发生关系菱形

2.2 属性四分类 ⚠️（转换规则常考）

类型定义例子转换处理方式
简单属性不可再分学号、性别直接变成关系模式的一列
复合属性可再拆成多个子属性"地址"=省+市+区+街道拆成多个简单属性分别作列
多值属性同一实体上可取多个值一个学生的"电话"（手机+家里+宿舍）拆出独立的关系模式（学号+电话）
派生属性可由其他属性算出来"年龄"由"生日"推出一般不存储，用时现算（可标注虚线椭圆）

口诀：复合拆列、多值拆表、派生不存。

❗【易错】多值属性不能"塞在同一列里逗号分隔"——那既不符合 1NF，也没法查询。考试标准答案永远是：多值属性单独建一个关系模式，主键里带上实体的码。

三、联系三种类型：1:1、1:n、m:n

3.1 定义 + 生活例子对照表

类型读法生活例子判断窍门
1:1（一对一）一个 A 对应一个 B班级 — 班长：一个班只有一个班长，一个班长只管一个班两边都问"能配几个"：都答 1
1:n（一对多）一个 A 对应多个 B班级 — 学生：一个班有多个学生，一个学生只属于一个班一边答 1，一边答 n
m:n（多对多）多个 A 对应多个 B学生 — 课程：一个学生选多门课，一门课被多个学生选两边都答"多个"

❗【易错】判断方向要双向都问一遍，只问一边容易把 1:n 看成 m:n。比如"学生—课程"：一个学生选多门课 ✔，再看一门课是否只被一个学生选——显然不是，所以是 m:n。

3.2 联系自身也可以带属性

联系也能有自己的属性。最经典的就是"成绩"挂在"学生—课程"的选修联系上，而不是挂在学生或课程上——因为"成绩"是某学生选某门课这个动作产生的，离开这个组合它没有意义。这在案例题里是必考的"属性归属"判断点。

口诀：属性挂在谁头上？——离开谁没意义就挂谁。

四、ER图符号规范表

图形/写法表示示例
矩形实体【学生】
椭圆属性（学号）
菱形联系＜选修＞
无向边（线段）连接实体与属性/联系——
线上标数字联系类型1、n、m
属性下加下划线码（主属性）学号

画图顺序口诀：先实体、再属性、后联系、线标数。

从需求到ER图：五步画图法（案例题照此执行）

步骤动作自查问题
① 找实体通读需求，圈出关键"名词"哪些东西需要独立存信息？
② 找属性给每个实体配特征，圈出码谁能唯一标识这个实体？
③ 定联系两两实体问关系，双向各问一遍，标 1/n/m一边能配几个、另一边能配几个？
④ 挂联系属性成绩、日期这类"动作产生"的信息挂菱形离开这个联系它还有意义吗？
⑤ 查漏补缺逐个检查多值属性、复合属性有没有一格塞多个值的？

❗【易错】需求里的"动词"多半是联系的候选（选课、借阅、订购），但也可能是实体（"订票"里的"票"）——判断标准回到"是否需要独立存储信息"：有自己的属性就升格为实体，没有就只是联系。

五、⚠️【必考】ER图转关系模式规则表（案例题核心引擎）

转换只有一个思想：每个实体先各变一个关系模式，然后看联系怎么落地。

联系类型转换规则结果生活例子落地
1:1任选一端，把对方的主键加进来作外键；或把联系拆成独立关系模式（两端主键任取一个作主键 + 联系自身属性）2 个（或 3 个）关系模式班级(班号,…) + 班长(学号,…,班号外键)；或 拆出"管理(班号,学号)"
1:n把 1 端的主键放进 n 端作外键；或拆成独立关系模式（主键 = n 端主键）2 个（或 3 个）关系模式学生(学号,…,班号外键)——班级主键塞进学生表
m:n必须拆成独立关系模式：两端主键组合成新关系模式的主键 + 联系自身属性3 个关系模式选修(学号,课程号,成绩)——学生表、课程表之外新增一张

口诀："1:1 任选一端、1:n 塞进多端、m:n 必须单独建表"。

❗【易错】案例题经典扣分点：m:n 联系不拆表，直接把"课程号"塞进学生表的一列里——这是阅卷现场最常见的丢分写法。后果：一个学生选 3 门课，学生基本信息被迫重复 3 行，数据冗余、修改异常全来了。正确姿势永远是第三张表：选修(学号, 课程号, 成绩)，主键 =（学号, 课程号）组合。

辅助记忆表格：

验收标准1:11:nm:n
新增独立关系？可选可选必须
外键放在哪任选一端n 端拆出的新表两端都放
新表主键一端主键或组合n 端主键两端主键组合

进阶转换：递归联系与三元联系（案例题偶现的加分项）

场景定义转换规则例子
递归联系同一实体内部的联系在关系模式中加一个"自引用"外键列员工(工号, 姓名, 领导工号)——领导工号引用本表工号
三元联系三个实体同时参与一个联系一般整体拆成独立关系模式，主键为三端主键组合（+联系属性）供应(供应商号, 项目号, 零件号, 数量)

❗【易错】三元联系不要急着拆成三个两两之间的 m:n——"供应商给项目供应零件"中，"数量"同时依赖三方，拆成三张两两表后"数量"就无处安放。判断标准：联系属性是否同时依赖多个参与方。

六、属性拆分的两条补充规则

场景规则举例
多值属性拆成独立关系模式（实体的码 + 该属性），主键为二者组合（或按需）电话(学号, 电话号码)
复合属性拆成多个简单属性各自作列地址 → 省、市、区、街道 4 列

和 5 里的 m:n 一样，都是"一个格子里不许塞多个值"思想的不同表现——这也是后面 05 篇规范化的第一块基石（1NF）。

七、局部ER图集成：三类冲突 + 消除冗余

大型系统往往各业务组先画局部 ER 图，再集成为全局 ER 图。集成的两步走：先解决冲突 → 再消除冗余。

标准集成流程（案例题可按此作答）：

步骤动作产出
① 合并按共同实体两两合并各局部 ER 图初步全局 ER 图
② 解决冲突逐项处理属性冲突 / 命名冲突 / 结构冲突消除矛盾的 ER 图
③ 消除冗余删冗余属性、冗余联系（结合查询需求权衡）优化后的全局 ER 图

口诀：先拼图、再拆架、后扫除——合并、解决冲突、消除冗余。

7.1 三类冲突（选择题 + 案例简答都爱考）

冲突类型含义举例
属性冲突属性类型/取值范围/单位不一致教务处"成绩"用百分制、学工处"成绩"用五级制；一处"学号"数值型、一处字符型
命名冲突同名不同义（一词多义）/ 不同名同义（多词一义）"教室"和"课堂"实为一个实体；两处"日期"含义不同
结构冲突同一对象在不同图中抽象级别不同学生在 A 图是实体、B 图成了属性；或同一实体属性集不同

口诀："属名构"三冲突——类型对不上、名字打架、同一对象长得不一样。

7.2 消除冗余

冗余种类是什么处理
冗余属性可由其他属性推导出删除或改挂派生属性（如"年龄"由"生日"可算）
冗余联系可由其他联系推导出如 A—B 已可通过 A—C—C—B 推得，则删 A—B 直连

❗【易错】消除冗余不是越狠越好——有些"可推导"的联系用于高频查询，保留反而提升效率。案例题答"全部删除可推导联系"拿不到满分，要补一句"结合查询需求权衡"。

八、三种经典逻辑模型对比（层次/网状/关系）

对比项层次模型网状模型关系模型
数据结构树形（双亲唯一）图（可有多个双亲）二维表
联系方式父子一对多任意连（记录+指针）外键 + 关系运算
典型系统IMSDBTG/CODASYLOracle、MySQL、SQL Server
优点结构简单清晰表达多对多更方便结构单一、理论扎实（关系代数）、高度非过程化
缺点多对多表达差、查询要逐层结构复杂、指针维护难查询效率依赖优化，需调优
形象比喻家谱族群关系网Excel 大表

口诀："层次是树、网状是图、关系是表。"

❗【易错】层次模型的实体间联系本质只支持 1:n（一个双亲多个子女）；多对多要靠冗余节点或拆分间接表达。题目问"哪种模型用二维表表达实体与联系"——答关系模型。

十、自测 5 题（改编自历年真题风格）

1. 在ER模型中，"学生的家庭住址"被拆分为省、市、区、街道四个数据项，则"家庭住址"属于（　）。 A. 简单属性 B. 复合属性 C. 多值属性 D. 派生属性

答案：B。能拆成多个子属性的是复合属性；转换时拆成 4 个简单属性列。

2. 某ER图中存在 m:n 联系"学生—选修—课程"，将其转换为关系模式时，正确的结果是（　）。 A. 在学生关系中增加一个"课程号"属性 B. 在课程关系中增加一个"学号"属性 C. 新建关系模式：选修(学号, 课程号, 成绩)，主键为（学号, 课程号） D. 将学生关系与课程关系合并为一个关系

答案：C。A、B 正是"m:n 不拆表"的经典错误写法，造成冗余；m:n 必须拆独立关系，两端主键组合作主键。

3. 将局部ER图集成为全局ER图时，"学生"在教务处ER图中是实体，在图书馆ER图中是"借阅"联系的属性，这类冲突属于（　）。 A. 属性冲突 B. 命名冲突 C. 结构冲突 D. 值域冲突

答案：C。同一对象在不同图中抽象级别不一致，是典型结构冲突。属性冲突指类型/单位/值域不一致；命名冲突指同名异义或异名同义。

4. 层次模型、网状模型、关系模型对应的数据结构分别是（　）。 A. 树、图、二维表 B. 图、树、二维表 C. 二维表、树、图 D. 树、二维表、图

答案：A。口诀"层次是树、网状是图、关系是表"直接锁定。

5.（综合题） 某企业信息管理系统中：

  • 实体员工（工号、姓名、性别、身份证号、多值属性"联系电话"）
  • 实体部门（部门号、部门名）
  • 联系属于：一个部门有多名员工，一名员工只属于一个部门
  • 实体项目（项目号、项目名），联系参与：一名员工可参与多个项目，一个项目由多名员工完成，联系属性为"承担角色"

【问题】判断"属于"和"参与"的联系类型，并写出转换后的全部关系模式（下划线表示主键，标注外键）。

解答：

  • "属于"：部门(1) — 员工(n)，是 1:n → 把部门主键塞进员工端。
  • "参与"：员工(m) — 项目(n)，是 m:n → 必须拆独立关系模式。

转换结果：

关系模式主键外键
员工(工号, 姓名, 性别, 身份证号, 部门号)工号部门号 → 部门
部门(部门号, 部门名)部门号—
项目(项目号, 项目名)项目号—
参与(工号, 项目号, 承担角色)(工号, 项目号)工号→员工；项目号→项目
联系电话(工号, 电话号码)(工号, 电话号码)工号 → 员工

扣分自查点：① 多值属性"联系电话"是否拆独立表？② "承担角色"是否正确落在参与表？③ 参与表主键是否为组合键？三处全部答对才算吃透本篇。
