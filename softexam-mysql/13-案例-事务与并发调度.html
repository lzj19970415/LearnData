13 案例实战四：事务与并发调度（最像"逻辑题"的一件套）

13.1 先说人话：几个事务抢数据，什么顺序才算"对"

想象两个柜台同时操作同一个账户：一个转账、一个计息，谁先谁后，结果会不一样吗？下午卷的并发题考的就是这件事——几个事务同时抢数据时，什么样的执行顺序（调度）才能得到正确结果。

这类题最不像"背诵题"，反而像逻辑推理题，套路固定、答案唯一，练熟了就是送分题。原理部分（ACID、封锁协议、2PL）见 06 事务ACID与并发控制，本篇的任务是把判断过程写成得分点：列冲突对、画优先图、下结论，一步不跳。

13.2 名词一句话复习（考前 10 分钟版）

名词一句话人话版
事务一组"要么全做、要么全不做"的数据库操作，比如一次转账
原子性（A）做了一半会自动全部退回，绝不留半拉子
一致性（C）事务做完，业务规则不被破坏（A 减少的钱 = B 增加的钱）
隔离性（I）并发执行的事务互相不干扰，效果像各自独占系统
持续性（D）一旦提交就永久生效，宕机也丢不了
调度多个事务的操作按时间排成的一个执行序列
可串行化并发执行的最终效果，等价于让这几个事务"按某个先后顺序排队执行"的效果——排得上队，就是正确调度

⚠️【必考】可串行化就是并发调度的"正确性判据"：能等价变换成某个串行调度 ⇒ 正确；不能 ⇒ 错误调度。

13.3 ⚠️【必考】判断调度是否可串行化（优先图完整示范）

事务登场（经典转账场景）：

  • T1：从 A 转出 100 给 B —— read(A); A:=A-100; write(A); read(B); B:=B+100; write(B)
  • T2：给 A 上浮 10% —— read(A); A:=A*1.1; write(A)

记号约定：下文用 r1(A) 表示 T1 的 read(A)、w1(A) 表示 T1 的 write(A)，其余类推。

第 0 步：先记住"什么算冲突"（四类操作规则）

两个操作算"冲突操作"，要同时满足三个条件：①同一数据项；②不同事务；③交换顺序会改变结果。

前后两个操作（不同事务、同一数据项）类型冲突吗能交换吗
读 → 读R-R不冲突能
读 → 写R-W冲突不能
写 → 读W-R冲突不能
写 → 写W-W冲突不能

❗【易错】同一事务内部的操作顺序永远不能变，不参与讨论；不同数据项上的两个操作永远不冲突。

给一个具体调度 S1

S1：r1(A) → w1(A) → r2(A) → w2(A) → r1(B) → w1(B)

第 ① 步：把所有冲突对列成表（别心算，写出来）

序号冲突对（同一数据项 A 上）类型优先图中的边
1r1(A) 在 w2(A) 之前R-WT1 → T2
2w1(A) 在 r2(A) 之前W-RT1 → T2
3w1(A) 在 w2(A) 之前W-WT1 → T2

B 上只有 T1 自己在操作，没有跨事务冲突对 ⇒ 不产生任何边。

第 ② 步：画优先图

图中只有一条边：T1 → T2（T1 的冲突操作在前，箭头从前操作的事务指向后操作的事务）。

第 ③ 步：看有没有"环"（沿着箭头走能绕回起点就是环）

  • 只有两个点、一条单向边 ⇒ 无环。

第 ④ 步：下结论

优先图无环 ⇒ S1 是冲突可串行化的，等价于串行调度"T1 先执行、T2 后执行"。

交换法复核一遍（养成双保险习惯）

  • S1 里 T2 的两个操作 r2(A)、w2(A) 都排在 w1(A) 之后；而 r1(B)、w1(B) 只碰 B，与 T2 的 A 操作不同数据项；
  • r2(A) 与 r1(B)：不同数据项 ⇒ 可交换；w2(A) 与 r1(B)、w1(B)：不同数据项 ⇒ 可交换；
  • 把 T2 整体挪到 T1 之后：r1(A) w1(A) r1(B) w1(B) r2(A) w2(A)——正是串行调度 T1→T2 ✓
  • 两种方法结论一致，放心写答案。

反例对照 S2：有环长什么样

S2：r1(A) → r2(A) → w2(A) → w1(A) → r1(B) → w1(B)

冲突对类型边
r1(A) 在 w2(A) 之前R-WT1 → T2
r2(A) 在 w1(A) 之前R-WT2 → T1
w2(A) 在 w1(A) 之前W-WT2 → T1

优先图：T1→T2 与 T2→T1 同时存在 ⇒ 成环 ⇒ S2 不可串行化，是错误调度。

交换法复核：r1(A) 与 r2(A) 是"读读"可以交换，但 T2 的 w2(A) 想挪到 T1 后面，必须跨过 r1(A)（W-R 冲突）和 w1(A)（W-W 冲突），一步都挪不动 ⇒ 无论如何变不成串行调度，坐实"不可串行化"。

作答模板（照这个骨架写）

① 列冲突对（写清 R-W / W-R / W-W 类型）； ② 由此构造优先图； ③ 图中存在环 Ti→…→Ti，故该调度不可串行化；或图中无环，故该调度可串行化，等价于串行调度 T_→T_。

13.4 2PL 题：怎么判断"遵守没遵守两段锁协议"

规则一句话：把事务的一生切成两个阶段——扩展阶段（只加锁、不释放） + 收缩阶段（只释放、不再申请新锁）。一旦开始解锁（跨过分界线），就再也不许申请新锁。

例 1：遵守 2PL 的加锁序列

步骤操作处于什么阶段
1lock-X(A)扩展：加锁
2lock-S(B)扩展：加锁
3读/写 A、B——
4unlock(A)收缩：解锁
5unlock(B)收缩：解锁

所有 lock 都排在所有 unlock 之前 ⇒ 遵守 2PL。

例 2：不遵守 2PL 的加锁序列

步骤操作问题出在哪
1lock-X(A)扩展：加锁
2修改 A——
3unlock(A)开始收缩
4lock-X(B)❌ 收缩阶段又申请新锁，违反 2PL

作答语言：

该事务在 unlock(A) 之后又执行了 lock-X(B)，即释放锁之后又申请新的锁，加锁与解锁没有分成两个不相交的阶段，故不遵守两段锁协议。

❗【易错】两条必记的边界：

  1. 遵守 2PL ⇒ 调度必可串行化；但 2PL 不能预防死锁（互相等锁照样发生）；
  2. 普通 2PL 可能造成级联回滚，所以有"严格 2PL"——要求 X 锁持有到事务结束（提交或回滚）才释放，InnoDB 实际采用的就是这类策略。

13.5 ⚠️【必考】三级封锁协议应用题："症状 → 诊断 → 处方"

三级协议速记表（规则背原话）：

级别加锁规则能防止
一级事务修改数据前必须先对其加 X 锁，直到事务结束才释放；读数据不加锁丢失修改
二级一级 + 事务读数据前必须先加 S 锁，读完即可释放丢失修改、脏读
三级一级 + 读前加 S 锁，直到事务结束才释放丢失修改、脏读、不可重复读

"症状 → 病因 → 处方"对照表（场景题直接对号入座）：

题目说系统出现了……说明当前协议缺什么（病因）处方
丢失修改（两次写互相覆盖）修改前没加 X 锁（或提前释放）改用一级封锁协议
脏读（读到别人未提交的数据）读前没加 S 锁（当前最多一级）改用二级封锁协议
不可重复读（两次读结果不一样）S 锁读完就放（当前最多二级）改用三级封锁协议

标准作答模板（三句话，背下来）：

① 系统当前采用的是__级封锁协议，因为__（写出缺陷：如"读数据前未加 S 锁""S 锁在读取完成后立即释放"）。 ② 该缺陷导致__（丢失修改/脏读/不可重复读）问题的发生。 ③ 改用__级封锁协议即可防止该问题，其加锁规则为__（把新一级的规则复述一遍）。

示范作答：题面"某系统采用一级封锁协议。统计事务在同一事务内两次读取同一账户余额，结果却不同，请分析原因并给出解决方案"：

系统当前采用的是一级封锁协议。一级协议只要求修改数据前加 X 锁并持有至事务结束，读数据前不加 S 锁，导致本事务两次读取之间，其他事务的提交/修改会被读进来，发生不可重复读。改用三级封锁协议即可防止：读数据前先加 S 锁且持有至事务结束才释放，使其他事务在此期间无法修改该数据，从而保证可重复读。

13.6 死锁处理：三种问法，三种答法

题目怎么问答什么（关键词一个都不能少）
如何预防死锁① 一次封锁法：事务开始时一次性申请全部所需锁；② 顺序封锁法：所有事务按同一固定顺序申请锁
如何检测死锁① 超时法：锁等待超过阈值即认定死锁；② 等待图法：事务等待图中出现回路（环）即判定死锁
发现死锁后如何处理/恢复选择一个撤销代价最小的事务，回滚并释放其持有的全部锁，让其他事务继续执行

❗【易错】问"预防"答"检测方法"不得分；问"处理"通常要答"检测 + 恢复"两段。DBMS 里死锁无法彻底杜绝，题眼往往是"以预防为辅、以检测恢复为主"。

13.7 ⚠️【必考】MySQL 运维场景题套路（近年新趋势）

原理见 06 事务ACID与并发控制（封锁与 2PL）、运维见 08 MySQL专项高频考点，这里只给场景题的标准答法。

13.7.1 长事务的危害与治理

危害一句话解释
长期持有锁阻塞排队的事务，引发大面积锁等待
undo 膨胀回滚日志无法清理，表空间持续增长
MVCC 旧版本堆积快照读要沿版本链爬很久，查询越来越慢
主从延迟从库重放一个大事务要花同样长的时间
回滚代价巨大一旦出错，回滚时间可能比执行还长

治理四板斧：① 开启 autocommit、把大事务拆小；② 事务内不做 RPC 调用、不等人工输入；③ 用 information_schema.innodb_trx 监控长事务；④ 对超长事务告警并人工介入。

-- 查找运行超过 60 秒的事务（长事务巡检）
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

13.7.2 隔离级别选择的标准答法

隔离级别一句话定位典型业务
READ UNCOMMITTED什么脏数据都可能读到，几乎不用——
READ COMMITTED只读提交过的数据，防脏读；锁持有短、并发好互联网高并发：商品列表、动态流
REPEATABLE READ同一事务内多次读结果一致；MySQL 默认级别财务对账、余额快照、报表
SERIALIZABLE完全串行，最安全也最慢强一致、低并发的小范围场景

标准作答句式：

该业务要求同一事务内多次读取同一数据得到一致结果（如对账、出报表），应选择 REPEATABLE READ；该业务并发量大、且能容忍两次读取之间数据变化（如商品列表刷新），选择 READ COMMITTED 可减少锁冲突、提高并发度。

13.7.3 锁等待 / 死锁排查四步法

步骤命令/动作看什么
①SHOW PROCESSLIST哪些会话处于 Waiting for lock 状态
②SHOW ENGINE INNODB STATUS"LATEST DETECTED DEADLOCK"段：最近一次死锁的两个事务各自在等谁的锁
③查 information_schema.innodb_trx（及锁信息表）定位具体哪条 SQL 在持有/等待锁
④优化给过滤条件补索引（缩小扫描范围 = 缩小锁范围）、把大事务拆小、统一多表的更新/加锁顺序

13.8 演练题（改编自历年真题风格）

演练题一：三个事务 + 两个调度，判断可串行化

题面：

  • T1：read(A); A:=A-100; write(A); read(B); B:=B+100; write(B)
  • T2：read(A); A:=A*1.1; write(A)
  • T3：read(B); B:=B+50; write(B)

调度 Sa：r1(A), w1(A), r2(A), w2(A), r1(B), w1(B), r3(B), w3(B) 调度 Sb：r2(A), r1(A), w1(A), w2(A), r3(B), r1(B), w3(B), w1(B)

问：Sa 与 Sb 是否为可串行化调度？说明理由。

【参考答案】

先分析 Sa 的冲突对：

数据项冲突对类型边
Ar1(A) 在 w2(A) 前R-WT1→T2
Aw1(A) 在 r2(A) 前W-RT1→T2
Aw1(A) 在 w2(A) 前W-WT1→T2
Bw1(B) 在 r3(B) 前W-RT1→T3
Br1(B) 在 w3(B) 前R-WT1→T3
Bw1(B) 在 w3(B) 前W-WT1→T3
  • 优先图只有两条边：T1→T2、T1→T3，无环 ⇒ Sa 可串行化，等价于 T1 先执行的串行调度（T2、T3 之间无公共数据项、无先后约束，顺序任意，如 T1→T2→T3）。

再分析 Sb 的冲突对：

数据项冲突对类型边
Ar2(A) 在 w1(A) 前R-WT2→T1
Ar1(A) 在 w2(A) 前R-WT1→T2
Aw1(A) 在 w2(A) 前W-WT1→T2
Br3(B) 在 w1(B) 前R-WT3→T1
Br1(B) 在 w3(B) 前R-WT1→T3
Bw3(B) 在 w1(B) 前W-WT3→T1
  • 优先图同时存在 T1→T2 与 T2→T1（环），以及 T1→T3 与 T3→T1（又一个环）⇒ Sb 不可串行化，是错误调度。

评分点表：

调度阅卷找什么关键词示意分值
SaA、B 两数据项冲突对各 3 条；优先图 T1→T2、T1→T3；"无环 ⇒ 可串行化"及等价串行次序6
Sb找出 T2→T1（或 T3→T1）方向的边；指出图中成环；"有环 ⇒ 不可串行化"结论6

演练题二：售票系统并发问题（场景题）

题面：某售票系统余票表 ticket(班次, 余票数)，某班次余票数为 1。两个售票窗口同时执行事务：读余票数 → 判断余票数 > 0 → 出票并将余票数减 1 → 写回。运行后出现：两个窗口都出票成功，但余票只减了 1。问： ①系统出现了什么并发问题？ ②应采用哪级封锁协议解决？ ③说明该协议的加锁规则。

【参考答案】

① 丢失修改。两个事务都读到"余票数 = 1"，各自判断通过、各写回"余票数 = 0"；T2 的写回把 T1 的写回覆盖了，两次出票只生效一次扣减，造成一票两卖。

② 改用一级封锁协议即可解决。

③ 加锁规则：事务修改数据前必须先对其加 X 锁，并保持到事务结束（COMMIT/ROLLBACK）才释放。这样 T1 持锁期间，T2 对同一条余票记录的加锁请求被阻塞等待；T1 提交并释放锁后，T2 才能加锁并读到最新值"余票数 = 0"，判断不通过、拒绝出票。

（加分项：在 MySQL 中可用悲观锁实现同样效果——SELECT 余票数 FROM ticket WHERE 班次='xxx' FOR UPDATE; 再执行扣减更新。）

评分点表：

问题阅卷找什么关键词示意分值
①"丢失修改"四字 + 用"两个事务都读到 1、写回互相覆盖"解释成因3
②一级封锁协议2
③写前加 X 锁；持有到事务结束才释放；后到事务等待的说明5
