06 事务ACID与并发控制（上午送分+下午案例第四大件）

师兄先说人话：事务 = 要么全干完、要么全没干的一整套动作。转账最典型：A 账户扣 500、B 账户加 500——这两步只许"都发生"或"都没发生"，最怕扣了钱没到账。数据库把这种"打包执行、要么全做要么全不做"的机制叫事务。上午考 ACID、三级封锁协议、2PL 都是送分题；下午案例最后一问常考并发调度、死锁、恢复，这一章一网打尽。

一、事务的定义与 SQL 写法

正式定义：事务是用户定义的一个数据库操作序列，这些操作要么全做、要么全不做，是一个不可分割的工作单位。

START TRANSACTION;                                            -- 开启事务（MySQL 也用 BEGIN）
UPDATE Account SET balance = balance - 500 WHERE id = 'A';   -- A 账户扣 500
UPDATE Account SET balance = balance + 500 WHERE id = 'B';   -- B 账户加 500
COMMIT;                                                       -- 提交：全部生效，永久保存
-- 若中途出错（比如第二条失败）：
ROLLBACK;                                                     -- 回滚：A 的扣款一并撤销，当无事发生

二、⚠️【必考】ACID 四大特性

特性英文人话实现手段
原子性Atomicity要么全干完，要么全没干，绝不留"半成品"undo 日志（回滚未完成事务）
一致性Consistency事务前后数据都符合所有规则（收支守恒、余额非负等）完整性约束 + 应用逻辑共同保证
隔离性Isolation多个事务并发执行互不干扰，像各自独占系统封锁 + MVCC（多版本并发控制）
持续性（永久性）Durability一旦提交成功，改动永久保存，断电也不丢redo 日志

口诀：原子靠 undo，一致靠约束，隔离靠锁，持久靠 redo。

上午考法：给一句描述问"体现哪个特性"，或给特性问"靠什么实现"。典型对号入座：

  • "断电后已提交的转账不丢" → 持续性；
  • "回滚后 A 扣的 500 又回来了" → 原子性；
  • "两人同时转账互不干扰" → 隔离性。

三、并发执行的三大问题（每个看数字）

多个事务同时跑、不加控制，就会出事。三大经典事故：

1. 丢失修改（两个写互相覆盖）

时刻事务 T1事务 T2
t1读票数 A=100
t2读票数 A=100
t3A=A-1，写回 99
t4A=A-1，写回 99 ❌

T2 把 T1 的修改覆盖了：实际卖出 2 张票，库存却只减了 1 张——T1 的修改"丢"了。

2. 不可重复读（同一行两次读，值变了）

时刻事务 T1事务 T2
t1读 A=100（准备计算）
t2读 A=100，改成 200，提交
t3再读 A=200 ❌

T1 在同一事务里两次读同一行，结果不一样——同一账户余额，一会儿 100 一会儿 200。

3. 读脏数据（读到了别人回滚的"半成品"）

时刻事务 T1事务 T2
t1把 A 从 100 改成 200（未提交）
t2读 A=200 ❌
t3回滚，A 恢复 100

T2 读到的 200 是个"根本没存在过"的值——脏数据。

问题一句话冲突类型
丢失修改两个写互相覆盖写-写
不可重复读同一行两次读，值不同中间被人改了
读脏数据读到未提交（还可能回滚）的值读-未提交写

补充：幻读是不可重复读的"表亲"——两次读结果集的行数变了（别人插/删了行）。不可重复读盯的是同一行的值，幻读盯的是行数。MySQL 隔离级别考题里两者会分开问。

四、封锁：X 锁与 S 锁

人话：锁就是给数据挂"门牌"——挂了"装修中"（X 锁）谁都别进，挂了"开放参观"（S 锁）大家可以一起参观但别动手。

锁全称什么时候加特点
X 锁（排他锁/写锁）eXclusive写数据前一旦挂上，别的事务读也不行、写也不行
S 锁（共享锁/读锁）Share读数据前大家可以同时读，但谁也别想写

相容矩阵（行 = T1 已持有，列 = T2 申请）：

T1 持有 \ T2 申请SX
S相容不相容
X不相容不相容

口诀：读读相容，读写互斥，写写互斥（只有 S+S 能共存）。

五、⚠️【必考】三级封锁协议

协议X 锁（写锁）S 锁（读锁）能防止的问题
一级封锁协议修改前加 X 锁，事务结束才释放读不加锁防丢失修改
二级封锁协议同一级读前加 S 锁，读完立即释放防丢失修改 + 脏读
三级封锁协议同一级读前加 S 锁，事务结束才释放防丢失修改 + 脏读 + 不可重复读

口诀：S 锁放得越晚，防得越多——读完就放（二级）止步于防脏读；攥到事务结束（三级）才能防不可重复读。

人话验证"三级为什么能防不可重复读"：T1 读 A 时加 S 锁并攥到事务结束 → T2 想改 A 得申请 X 锁 → 与 S 锁冲突，只能等 → T1 第二次读 A，值没变 ✅。二级协议里 T1 读完就放锁，T2 随后就能改 A，T1 再读就变了 ❌。

❗【易错】三个协议防的问题数量别记错：

  • 一级防 1 个：丢失修改；
  • 二级防 2 个：+ 脏读；
  • 三级防 3 个：+ 不可重复读。

选择题常拿"三级协议不防丢失修改"当诱饵——防，别上当。

六、活锁与死锁

概念现象人话
活锁T1 申请锁被拒后等待，系统却一直优先满足 T2、T3…，T1 永远等下去排队总被插队，活活饿着
死锁多个事务互相持有对方想要的锁，谁也不撒手两人在独木桥中间顶牛

活锁的解决：先来先服务（FCFS）——按申请顺序排队，不许后来的插队。

死锁的处理分三段，逐级背：

环节方法思路 / 缺点
预防一次封锁法每个事务一次把要用的数据全锁上
顺序封锁法所有事务按统一顺序加锁
检测超时法等待超过规定时限就认定死锁
等待图法事务等待图中出现回路 ⇔ 死锁
恢复撤销代价最小的事务从死锁事务中挑一个"最便宜"的撤销（牺牲品 victim），释放它的锁，让其他事务继续；之后重启该事务

七、可串行化调度

正式定义：多个事务并发执行，当且仅当其结果与某一次串行执行的结果相同时，该并发调度才是正确的，称为可串行化调度。可串行性是并发事务正确性的唯一准则。

概念含义
串行调度一个事务全部执行完，再执行下一个
并发调度多个事务的操作交错执行
可串行化调度并发调度结果与某个串行调度相同 ⇒ 正确

判断方法一：交换相邻不冲突操作

什么算"冲突"：两个操作属于不同事务、操作同一数据项、且至少有一个是写。

两个操作是否冲突
同一事务的两个操作不冲突（顺序不许换，不用管）
不同事务、不同数据不冲突
不同事务、同一数据、读-读不冲突
不同事务、同一数据、读-写 / 写-读 / 写-写冲突（不能随便换）

小例子：T1 只存取 A（A=A+100），T2 只存取 B（B=B-100）。

调度 S1：R1(A) → R2(B) → W1(A) → W2(B)

T1 只碰 A、T2 只碰 B，谁也不挡谁——把 R2(B)、W2(B) 整体挪到最前（它们与 W1(A) 数据不同，可交换），得到：

R2(B) → W2(B) → R1(A) → W1(A)

这正是串行调度"先 T2 后 T1"⇒ S1 可串行化 ✅。

判断方法二：优先图（前驱图）——考试主力

步骤：每个事务一个节点；扫一遍调度，凡是冲突对（前操作属 Ti、后操作属 Tj、i≠j）就画一条 Ti → Tj 的边；图无环 ⇔ 冲突可串行化。

小例子（有环）：

调度 S2：R1(A) → R2(A) → W1(A) → W2(A)

冲突对排查：R1(A) 在 W2(A) 前（读-写冲突）→ 边 T1→T2；R2(A) 在 W1(A) 前 → 边 T2→T1。T1→T2→T1 成环 ⇒ 不可串行化 ❌（这正是"丢失修改"型调度）。

八、⚠️【必考】两段锁协议（2PL）

定义：每个事务对锁的管理分两段：

阶段能干什么不能干什么
扩展阶段（加锁段）申请并获得任何锁释放任何锁
收缩阶段（解锁段）释放任何锁申请新锁
事务 T1（遵守 2PL）：
lockX(A)          ← 扩展阶段：只加不放
A = A - 100
lockS(B)          ← 仍在扩展阶段，可以继续加
B = B + 100
unlock(A)         ← 第一次释放：从此进入收缩阶段
unlock(B)         ← 只放不加

❗反例：unlock(A) 之后再 lockS(C)——释放后又加新锁，违反 2PL。

核心结论（一字不差背）：

  1. 若并发执行的所有事务都遵守 2PL，则对这些事务的任何并发调度都是可串行化的——2PL 是可串行化的充分条件；
  2. ❗【易错】遵守 2PL 不能防止死锁（大家都遵守 2PL，仍可能互相等待）；
  3. ❗【易错】可串行化的调度不一定遵守 2PL——2PL 是充分条件，不是必要条件。

上午考法：四句话挑错误的，"遵守两段锁协议就不会产生死锁"是常驻错误选项。

九、MySQL 四种隔离级别

隔离级别 = 数据库对并发问题"管多严"的档位。MySQL（InnoDB）设置语法：

SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
隔离级别中文脏读不可重复读幻读说明
READ UNCOMMITTED读未提交可能可能可能不加锁随便读，等于裸奔
READ COMMITTED读已提交防止可能可能只读别人已提交的数据
REPEATABLE READ可重复读防止防止可能InnoDB 默认；InnoDB 实际用间隙锁在很大程度上避免幻读
SERIALIZABLE串行化防止防止防止全部串行执行，最安全也最慢

❗【易错】

  • 默认级别是 REPEATABLE READ（可重复读），别选成 READ COMMITTED（那是 Oracle、PostgreSQL 的默认）；
  • 按标准答案，REPEATABLE READ 不能防幻读；InnoDB 实际用间隙锁缓解了幻读，考试以标准答案为准。

十、数据库恢复

四类故障

故障人话恢复要点
事务内部故障程序逻辑错误、运算溢出、违反完整性约束等非预期中断强制回滚该事务（UNDO）
系统故障（软故障）断电、死机、OS 崩溃——内存丢了、磁盘还在重启后：未提交事务 UNDO，已提交未写盘的事务 REDO
介质故障（硬故障）磁盘坏道、磁头碰撞——磁盘也丢了用后备副本 + 日志重建数据库
计算机病毒病毒破坏数据文件防杀结合；靠备份 + 日志恢复

转储（备份）

划分角度方式特点
按时机静态转储转储期间停止一切事务，副本一致；牺牲可用性
动态转储边运行边转储，不打扰业务；副本不保证一致，必须配合日志
按数量海量转储（全量）整库复制；恢复简单，费时费空间
增量转储只复制上次转储之后变化的数据；省时省空间，恢复要层层叠加
差量转储只复制上次全量转储之后变化的数据；介于两者之间

日志文件与运行记录优先原则

日志记录什么：事务开始/结束（COMMIT/ROLLBACK）标记 + 每次更新操作的前像（改前值）与后像（改后值）。

⚠️运行记录优先原则（WAL）：先写日志，后写数据库。原因：日志是"黑匣子"——只要日志写下了，就算数据没来得及写盘就崩了，也能靠日志把没做的补上（REDO）、把做错的撤销（UNDO）；反过来先改数据再补日志，日志没写就崩了，谁也不知道改过什么——无法恢复。

UNDO / REDO 各干什么

动作对象做法人话
UNDO（撤销）未提交（未完成/回滚）的事务按日志反向扫描，执行相反操作恢复原值做了没"签收"，退回去
REDO（重做）已提交但尚未写盘的事务按日志正向扫描，重新执行一遍签收了但没落袋，补落袋

检查点技术

作用：系统定期在日志中打"检查点"，并把此刻内存缓冲区的数据写回磁盘。恢复时从检查点开始向后处理，之前的无需再管。

好处人话
大幅缩短恢复时间不用从头翻整本日志
减少扫描的日志量只处理检查点之后的记录
减少系统重启开销恢复快，宕机影响窗口小

考前速记卡

  • 事务 = 要么全干要么全不干；SQL 三件套：START TRANSACTION / COMMIT / ROLLBACK
  • ACID：原子-undo、一致-约束、隔离-锁、持续-redo
  • 三大并发问题：丢失修改（写覆盖）、不可重复读（同行值变）、脏读（读未提交）；幻读盯行数
  • 锁：X 写锁全挡、S 读锁共享；读读相容，读写/写写互斥
  • 三级封锁协议：S 锁放得越晚防得越多；一级防丢失修改，二级 + 脏读，三级 + 不可重复读
  • 活锁 → 先来先服务；死锁 → 预防（一次/顺序封锁法）、检测（超时法/等待图有环）、恢复（撤代价最小者）
  • 可串行化：结果与某串行调度相同；优先图无环 ⇔ 冲突可串行化
  • 2PL：扩展只加、收缩只放；遵守 2PL ⇒ 必可串行化（充分条件）；不防死锁；可串行化不一定守 2PL
  • MySQL 默认隔离级别：REPEATABLE READ（防脏读 + 不可重复读，标准上不防幻读）
  • 恢复：故障四类（事务内部/系统/介质/病毒）；转储（静态动态 / 海量增量差量）；先写日志后写库；UNDO 撤未提交、REDO 重做已提交；检查点缩短恢复时间

自测 5 题（改编自历年真题风格）

1. 关于事务特性的实现手段，下列对应关系错误的是（　） A. 原子性 —— undo 日志 B. 持续性（永久性）—— redo 日志 C. 隔离性 —— 封锁机制 D. 一致性 —— 完全由数据库自动保证，与应用逻辑无关

2. 遵守三级封锁协议时，能防止的问题是（　） A. 仅丢失修改 B. 丢失修改和读脏数据 C. 丢失修改、读脏数据和不可重复读 D. 丢失修改、读脏数据、不可重复读和死锁

3. 关于两段锁协议（2PL），错误的是（　） A. 事务分为扩展阶段和收缩阶段，扩展阶段只能加锁不能放锁 B. 所有事务都遵守 2PL 时，并发调度必为可串行化调度 C. 所有事务都遵守 2PL 时，不会发生死锁 D. 可串行化的调度不一定遵守 2PL

4. MySQL（InnoDB）的默认事务隔离级别是（　） A. READ UNCOMMITTED　　B. READ COMMITTED　　C. REPEATABLE READ　　D. SERIALIZABLE

5. T1 的操作序列为 R1(A)、W1(A)；T2 的操作序列为 R2(A)、R2(B)。某并发调度为：R2(A) → R1(A) → W1(A) → R2(B)。判断该调度是否为冲突可串行化调度，并说明理由。

答案与解析

  1. D。一致性靠完整性约束 + 应用逻辑共同保证，事务执行结果对不对和应用逻辑有关，"完全自动保证"绝对化错误。A、B、C 均为标准对应关系。
  2. C。三级封锁协议防"三害"：丢失修改、脏读、不可重复读。死锁不是封锁协议能"防"的问题（加锁本身反而可能引发死锁），D 错。
  3. C。遵守 2PL 不防死锁；B、D 恰是 2PL"充分不必要"的两面——遵守必可串行化，但可串行化不必遵守。
  4. C。InnoDB 默认 REPEATABLE READ（可重复读），可防脏读与不可重复读；按标准答案仍可能发生幻读。
  5. 标准作答：该调度是冲突可串行化调度。理由：
    • 逐一排查冲突操作对：R2(A) 与 W1(A)（不同事务、同一数据、读-写）→ 冲突，且 R2(A) 在前，画边 T2→T1；R1(A) 与 R2(A) 是读-读，不冲突；W1(A) 与 R2(B) 数据不同，不冲突。
    • 优先图只有一条边 T2→T1，无环 ⇒ 该调度冲突可串行化，等价于串行调度"先 T2 后 T1"。
    • 验证：R2(B) 与 W1(A)、R1(A) 均不冲突，可交换到最前，得 R2(A) → R2(B) → R1(A) → W1(A)，恰为 T2 先、T1 后的串行调度。
