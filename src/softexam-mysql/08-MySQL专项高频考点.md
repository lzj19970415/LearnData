# 08 MySQL专项高频考点（上午送分+下午运维场景题的弹药库）

## 一、人话开场：把 MySQL 拆成"接待处-审批科-仓库"三层来记

把 MySQL 想成一家公司，一共三层：

- **接待处（连接层）**：门卫查工牌（账号密码认证）、登记来访（连接管理）、限制同时在场的客人数量（最大连接数）。
- **审批科（SQL 层）**：接单看懂写的是什么（解析 SQL）、规划最优办事路线（优化器）、问问最近有没有人办过一样的业务（查询缓存）、盖各种章（内置函数、存储过程、触发器、视图）。
- **仓库（存储引擎层）**：真正存取货物的地方——而且仓库是**外包**的，哪家承包商（InnoDB / MyISAM）都能接活、随插随换（插件式架构）。

记住这张三层图，本篇所有考点都能挂进去：索引是仓库的货架规则，三日志是仓库和审批科各自的账本，锁是仓库的安保规则，主从复制是"把流水账抄送给分店"。近几年的趋势是 MySQL 运维场景题越出越多，**上午下午都会考**，这篇就是你的弹药库。

## 二、⚠️【必考】MySQL 逻辑架构

| 层次 | 负责什么 | 关键词 |
| --- | --- | --- |
| 连接层 | 连接处理、身份认证、安全控制（SSL）、线程管理、连接池 | 一个客户端连接 = 一个服务端线程 |
| SQL 层（服务层） | SQL 解析、查询优化、查询缓存、跨存储引擎的通用功能 | 解析器、优化器、缓存、内置函数、存储过程/触发器/视图 |
| 存储引擎层 | 数据和索引的真实存储与读取，**插件式**架构 | InnoDB（默认）、MyISAM、Memory 等 |

三个常考小点：

- MySQL 是**单进程多线程**架构：一个 mysqld 进程，每来一个连接分配一个线程，不是 Oracle 那种多进程架构。
- 日志归属：**binlog 属于 SQL 层（Server 层）**，**redo log / undo log 属于 InnoDB 引擎层**——这个归属关系下午案例题考过。
- 查询缓存在 MySQL 8.0 已被移除（命中率太低，表一有更新整批失效），当背景知识了解即可。

## 三、⚠️【必考】InnoDB vs MyISAM

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务支持 | **支持**（ACID、提交/回滚） | 不支持 |
| 锁粒度 | **行级锁**，并发写性能好 | **表级锁**，一写锁全表 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | **支持**（靠 redo log，crash-safe） | 不支持，损坏后一般靠 REPAIR 修表 |
| 索引结构 | **聚簇索引**，主键索引叶子存整行数据 | 非聚簇索引，叶子存数据文件的地址指针 |
| 适用场景 | OLTP：增删改频繁、要事务要安全的业务表 | 以读为主、极少修改的报表/日志/统计表 |

⚠️【必考】**InnoDB 是 MySQL 5.5+ 的默认存储引擎**（5.5 之前的默认是 MyISAM）——上午选择题的送分点。

人话：InnoDB 是带保镖的全能管家——贵一点（占空间、稍慢）但事务、行锁、外键、崩溃恢复全都有；MyISAM 是老实仓库员——查询飞快，但一摔就失忆、一写就锁全表。

## 四、⚠️【必考大头】索引原理

### 4.1 B+ 树为什么适合数据库

先背三个理由，再对上类比：

| 理由 | 人话解释 |
| --- | --- |
| 树矮胖 → IO 次数少 | 3~4 层就能装下千万级行，查一次数据只需 3~4 次磁盘 IO |
| 叶子节点串成**有序链表** → 范围查询快 | BETWEEN、>、ORDER BY 顺着链表扫就行，不用回到树根反复找 |
| 非叶子节点**只存键、不存数据** → 扇出大 | 一页 16KB 能放几百个键，"目录"更厚、分支更多，树更矮 |

书的目录类比：查"主从复制"在哪一页——先翻总目录（根节点）→ 定位章目录（非叶子节点）→ 定位小节页码（叶子节点），翻 3 次目录就能定位，不必逐页翻书。每个"目录页"对应磁盘一页 16KB，节点大小与页对齐，一次 IO 读一页。

对比一句 B 树：B 树**每个节点都存数据**，一页放不了几个键，树更高、范围查询也弱；B+ 树把所有数据统一压到叶子层并串成链表——所以 MySQL 的索引用 B+ 树。

### 4.2 聚簇索引、二级索引、回表、覆盖索引

四个概念一环扣一环：

- **聚簇索引（主键索引）**：数据行本身**按主键有序存放**，叶子节点存的就是**整行数据**——"索引即数据，数据即索引"，一张表只能有一个。
- **二级索引（辅助索引）**：自己单独一棵 B+ 树，叶子节点存的是**主键值**（不是行地址！这是 InnoDB 和 MyISAM 的关键区别）。
- **回表**：走二级索引先查到主键值，再拿主键去聚簇索引里捞整行数据——这次二次查找就叫**回表**。
- **覆盖索引**：查询要的列**全部都在索引里**，不用回表，EXPLAIN 的 Extra 显示 `Using index`——性能优秀的标志，也是建索引时的优化目标。

| 概念 | 叶子节点存什么 | 取整行数据要不要二次查找 |
| --- | --- | --- |
| 聚簇索引 | 整行数据 | 不用（索引即数据） |
| 二级索引 | 主键值 | 要（回表） |
| 覆盖索引 | 主键值 + 索引自身列 | 不用（要查的列索引里都有） |

❗【易错】为什么建表推荐**自增整型主键**：① 自增主键顺序追加，写满一页再开新页，几乎不发生页分裂；② 二级索引每个叶子都复制一份主键，主键越短，所有索引都越小。

### 4.3 最左前缀原则【场景题最爱】

联合索引 `idx(A, B, C)` 相当于一口气建了 (A)、(A,B)、(A,B,C) 三套索引，查询条件必须**从最左列 A 开始、连续命中**：

| 查询条件 | 能否用上 idx(A,B,C) | 说明 |
| --- | --- | --- |
| `WHERE A=1` | ✅ 用到 A | 最左列在场 |
| `WHERE A=1 AND B=2` | ✅ 用到 A、B | 连续命中 |
| `WHERE A=1 AND B=2 AND C=3` | ✅ 三列全用上 | 完整命中 |
| `WHERE A=1 AND C=3` | ⚠️ 只用到 A | C 跳过了 B，只能靠 A 过滤后回表筛 C |
| `WHERE A>1 AND B=2` | ⚠️ 只用到 A | A 用了**范围**，B 就断了 |
| `WHERE B=2` / `WHERE C=3` | ❌ 完全用不上 | 缺最左列 A |
| `WHERE B=2 AND C=3` | ❌ 完全用不上 | 缺最左列 A |

口诀：**"带头大哥（A）不能死，中间兄弟不能断；范围之后全作废。"**

### 4.4 ❗【易错】索引失效六大场景

| # | 失效场景 | 反面教材 |
| --- | --- | --- |
| 1 | 对索引列**用函数或运算** | `WHERE YEAR(create_time)=2026`、`WHERE id+1=10`、`WHERE LEFT(name,1)='张'` |
| 2 | **隐式类型转换**：字符串列传数字 | 列是 VARCHAR 却写 `WHERE phone=13800000000`（没加引号） |
| 3 | **LIKE 以 % 开头** | `WHERE name LIKE '%张'`（`'张%'` 前缀匹配可以用索引） |
| 4 | **OR 两侧有非索引列** | `WHERE name='张三' OR age=20`，age 没索引则整条 SQL 放弃索引 |
| 5 | **!= / <> / NOT IN / NOT EXISTS** | `WHERE status != 1` |
| 6 | 联合索引**不满足最左前缀** | idx(A,B,C) 却 `WHERE B=2` |

❗细节（真题级易错）：隐式转换是"**字符串列传数字**"才失效——MySQL 会把**列**转成数字再比，等价于给列套了 CAST 函数，回到场景 1。反过来，**数字列传字符串** `WHERE id='10'` **不失效**（被转换的是常量）。上午题就爱拿这个细节设坑。

## 五、⚠️【必考】事务三日志：redo / undo / binlog

| 日志 | 归属哪层 | 记录内容 | 保证什么 / 干什么用 | 人话 |
| --- | --- | --- | --- | --- |
| redo log（重做日志） | InnoDB 引擎层 | 数据页的**物理修改** | **持久性**；崩溃后恢复已提交的数据 | 改动先记备忘录（WAL），之后慢慢刷盘 |
| undo log（回滚日志） | InnoDB 引擎层 | **逻辑反向操作**（INSERT 记对应的 DELETE） | **原子性**（回滚依据）；**MVCC 的基础**（留旧版本给别人读） | 反悔药：记下"怎么撤销" |
| binlog（二进制日志） | Server 层 | 逻辑变更（语句/行事件） | **主从复制 + 时间点恢复** | 送给从库和备份用的流水账 |

配套记忆：**redo 保 D（持久），undo 保 A（原子）+ 喂 MVCC，binlog 管复制恢复；隔离性 I 靠 MVCC + 锁，一套 ACID 就齐了。**

WAL（Write-Ahead Logging，先写日志）：改动先顺序写日志（快），再慢慢随机刷数据页（慢）；万一中途崩溃，凭日志把已提交的改动重做回来。

### 5.1 两阶段提交（简述）

一次事务提交时，引擎层的 redo log 和 Server 层的 binlog **必须一致**，否则主从数据、备份恢复都会错位：

```text
1. 写 redo log，状态置为 prepare
        ↓
2. 写 binlog（必须写成功）
        ↓
3. redo log 状态置为 commit，事务提交完成
```

崩溃恢复的判据：redo 已 prepare 而 binlog **完整** → 提交；binlog 不完整 → 回滚。这保证两份日志"同生共死"，就是 MySQL 内部的**两阶段提交**（2PC）。

## 六、InnoDB 的锁与死锁排查

| 锁类型 | 锁住的范围 | 作用 | 人话 |
| --- | --- | --- | --- |
| 行锁（Record Lock） | 索引上的**某一条记录** | 精确锁一行，并发最好 | 锁"某个座位" |
| 间隙锁（Gap Lock） | 两条索引记录之间的**空隙** | 防止别的事务往缝里插入数据（防幻读） | 锁"空座的缝"，不许人插进来 |
| 临键锁（Next-Key Lock） | 行锁 + 间隙锁（左开右闭区间） | InnoDB 在可重复读（RR）级别下的默认加锁单位 | 一排座位 + 旁边的缝一起锁 |

❗【场景题高频】InnoDB 的行锁是**加在索引上的**：WHERE 条件没走索引（或该列根本没索引），就会退化为**锁住全表所有记录**——"行锁变表锁"，并发瞬间崩掉。这就是"过滤条件列必须建索引"的深层理由。

死锁排查三板斧：

```sql
SHOW ENGINE INNODB STATUS\G   -- 看 LATEST DETECTED DEADLOCK 段：谁在等谁
SHOW PROCESSLIST;              -- 看当前所有连接在执行什么
KILL <id>;                     -- 杀掉僵持的连接
```

死锁预防：① 事务尽量小、尽量短；② 多表/多行更新**按固定顺序**访问；③ InnoDB 默认开启死锁检测，会自动回滚代价小的一方（了解即可）。

## 七、⚠️【必考】主从复制原理

### 7.1 复制四步（背顺序，下午画图题考过）

```text
主库执行事务，写入 binlog
        │  ① 主库 Binlog Dump 线程读取 binlog，发送给从库
        ▼
从库 IO 线程接收 binlog，写入本地 relay log（中继日志）
        │  ② 从库 SQL 线程读取 relay log，重放执行
        ▼
从库数据追平主库，循环往复
```

| 角色 | 职责 |
| --- | --- |
| 主库 Binlog Dump 线程 | 把 binlog 事件推送给从库 |
| 从库 IO 线程 | 接收 binlog，写进本地 relay log |
| 从库 SQL 线程 | 从 relay log 读事件，重放执行 |

口诀：**"主写 binlog，dump 发；IO 收下写 relay；SQL 读着重放忙。"**

### 7.2 异步复制 vs 半同步复制

| 方式 | 主库提交的等待条件 | 特点 |
| --- | --- | --- |
| 异步复制（默认） | 提交后立刻返回客户端，**不等从库** | 性能最好；主库宕机时最后一批 binlog 可能还没传出去 → 丢数据 |
| 半同步复制 | **至少 1 个从库**收到 binlog 并写入 relay log 回执后，才向客户端返回成功 | 性能略降；保证至少一台从库不丢，兼顾安全 |

### 7.3 主从延迟：原因与应对

延迟的本质：**从库重放速度 < 主库写入速度**。`SHOW SLAVE STATUS\G` 里的 `Seconds_Behind_Master` 越大越严重。

常见原因：① 从库 SQL 线程单线程重放（5.7 以前）；② 主库大事务、大批量写入；③ 从库硬件差、还扛着查询压力；④ 主从之间网络抖动。

应对清单：大事务拆小；开启并行复制（MTS）；从库只读、不加业务压力；持续监控延迟；对"写完必须立刻读到"的业务强制读主库。

### 7.4 读写分离架构（文字描述）

```text
                         ┌──> 主库：承接所有写操作（INSERT / UPDATE / DELETE）
应用 ──> 读写分离中间件
                         └──> 从库1 / 从库2：分担 SELECT 查询压力
              ▲
              └── 主库变更靠 binlog 复制搬运到从库（异步或半同步）
```

一句话：**写走主库，读走从库**。最大风险点：复制有延迟，刚写完立刻去从库读，可能读到旧数据——强一致读必须路由回主库。

## 八、性能优化套路【下午场景题模板】

### 8.1 发现慢 SQL：慢查询日志

```ini
# my.cnf 配置
slow_query_log = ON          # 开启慢查询日志
long_query_time = 2         # 执行超过 2 秒才算慢查询
```

```sql
-- 或在 mysql 里动态开启
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 2;
SHOW VARIABLES LIKE 'slow_query%';   -- 查看开关与文件位置
```

### 8.2 ⚠️【必背】EXPLAIN 关键列解读

用法：在 SELECT 前加 `EXPLAIN`，重点看三列：

| 列 | 看什么 |
| --- | --- |
| type | **访问类型，性能从好到差**：system > const > eq_ref > ref > range > index > ALL。至少到 range / ref 算合格，**ALL（全表扫描）必须优化** |
| rows | 预估扫描行数，越少越好 |
| Extra | `Using index` 好（覆盖索引）；`Using filesort` 要警惕（排序没走索引）；`Using temporary` 要警惕（用了临时表） |

type 档位人话对照：

| 档位 | 含义 | 人话 |
| --- | --- | --- |
| system / const | 主键或唯一索引等值查询，最多 1 行 | 按门牌号直接取 |
| eq_ref | JOIN 时被驱动表用主键/唯一索引匹配，外层每行最多命中 1 行 | 按身份证号对人 |
| ref | 普通索引等值查询 | 按姓氏找，可能命中多个 |
| range | 索引范围扫描（BETWEEN、>、IN） | 按年级范围找 |
| index | 扫整棵索引树 | 翻遍整本目录 |
| ALL | 全表扫描 | 逐页翻完一本书，最差 |

### 8.3 优化思路清单（下午按这个顺序作答不丢分）

1. **建合适的索引**：给 WHERE / ORDER BY / JOIN ON 的列建索引，联合索引按"最左前缀 + 等值列在前、范围列在后"设计；
2. **不写 SELECT \***：只取需要的列，争取覆盖索引免回表；
3. **深分页优化——延迟关联**：先在覆盖索引里捞出目标主键，再回表取整行；

```sql
-- 慢：要扫过前 100 万行才取 20 行
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;
-- 快：延迟关联，子查询只在索引上扫 20 个主键
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id;
```

4. **大事务拆小**：缩短锁持有时间，顺带减小主从延迟；
5. **还扛不住再升级架构**：加缓存（Redis）→ 读写分离 → 垂直拆分 → 最后才水平分库分表（顺序本身就是考点）。

## 九、分库分表：垂直 vs 水平

| 方式 | 怎么拆 | 人话 | 例子 |
| --- | --- | --- | --- |
| 垂直分库 | 按**业务域**把表分到不同库 | 按部门把档案柜分到不同房间 | 用户库、订单库分开 |
| 垂直分表 | 按**列**把一张宽表拆成多张 | 不常用的大字段挪去另一张表 | 商品主表 / 商品详情表（大文本） |
| 水平分表 | 按**行**拆到同一库的多张表 | 一本太厚的账本分几本记 | orders 拆成 orders_0 ~ orders_99，按 id % 100 路由 |
| 水平分库 | 按**行**拆到不同机器的多个库 | 账本分到各分店 | 路由策略：哈希取模 / 按时间 / 按范围 |

⚠️ 什么时候才需要分库分表（考点在"顺序"与"代价"）：

- 经验阈值：**单表约 1000 万行以上**（或 2GB+），B+ 树过高、SQL 明显变慢；
- 前提：索引优化、SQL 优化、加缓存、读写分离**全做过还是扛不住**，才动手分库分表——它是**最后手段**；
- 代价：跨库 JOIN、分布式事务、扩容数据迁移全都变麻烦——**能不拆就不拆**。

## 十二、自测 5 题（改编自历年真题风格）

**1.** 以下关于 InnoDB 与 MyISAM 的说法，**错误**的是（　）。

A. InnoDB 支持事务与外键，MyISAM 均不支持
B. InnoDB 使用行级锁，MyISAM 使用表级锁
C. InnoDB 的主键索引是聚簇索引，叶子节点保存整行数据
D. MyISAM 是 MySQL 5.5 及以上版本的默认存储引擎

**答案：D**。5.5+ 的默认引擎是 **InnoDB**，MyISAM 只是 5.5 之前的老默认。A、B、C 均为两者标准差异；C 要记牢：InnoDB 二级索引叶子存主键值，MyISAM 索引叶子存数据地址指针。

**2.** 表 t 上建有联合索引 idx(a, b, c)，以下查询**能用上**该索引的是（　）。

A. `SELECT * FROM t WHERE b=1 AND c=2;`
B. `SELECT * FROM t WHERE c=3;`
C. `SELECT * FROM t WHERE a=1 AND b=2;`
D. `SELECT * FROM t WHERE b=1;`

**答案：C**。最左前缀原则：必须从最左列 a 开始、连续命中。A、B、D 都缺了最左列 a，索引完全用不上；C 连续命中 a、b 两列。

**3.** name 为 VARCHAR 列且已建索引，以下查询**不能**利用该索引的是（　）。

A. `WHERE name = '张三'`
B. `WHERE name LIKE '张%'`
C. `WHERE name = 13800`
D. `WHERE name BETWEEN '李' AND '王'`

**答案：C**。字符串列传**数字**发生隐式类型转换，等价于给 name 列套了 CAST 函数，索引失效。A 等值查询、B 前缀匹配、D 范围扫描都能正常走索引。

**4.** InnoDB 中，保证事务**持久性**、并可在崩溃后恢复已提交数据的日志是（　）。

A. undo log
B. redo log
C. binlog
D. 慢查询日志

**答案：B**。redo log 重做日志保证持久性（D），是崩溃恢复的依据；undo log 保证原子性（A）并作为 MVCC 基础；binlog 服务于主从复制与时间点恢复；慢查询日志只是性能调优工具。

**5.** MySQL 主从复制中，负责读取中继日志（relay log）并重放 SQL 的线程是（　）。

A. 主库 Binlog Dump 线程
B. 从库 IO 线程
C. 从库 SQL 线程
D. 主库 SQL 线程

**答案：C**。复制链路：主库 Dump 线程发 binlog → 从库 IO 线程收下写 relay log → **从库 SQL 线程**读 relay log 重放。三个线程各司其职，顺序不能背反。
