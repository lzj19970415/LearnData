# 09 案例答题总纲与评分套路（先学会拿分，再谈学懂）

> 学之前先记一句大实话：**下午题不是作文比赛，是踩点给分的"填空题"。** 阅卷老师在你的答案上停留的时间以秒计，他不是在欣赏文采，而是在**找关键词**——扫到"参照完整性"给一分，扫到"传递函数依赖"再给一分。你写了三行没有关键词，不如写一行全踩在点上的。
>
> 所以这一篇不教知识点，只教一件事：**怎么把"会的东西"变成"卷面上的分"。** 知识本身请回去翻 01~08 篇，案例四大件的实战演练见 [10 案例-ER图与关系模式设计](10-案例-ER图与关系模式设计.md)、[11 案例-SQL建表与查询](11-案例-SQL建表与查询.md)、[12 案例-候选键与范式分解](12-案例-候选键与范式分解.md)、[13 案例-事务与并发调度](13-案例-事务与并发调度.md)。

## 一、先认清对手：下午卷长什么样

| 项目 | 内容 |
| --- | --- |
| 科目名称 | **应用技术**（大家习惯叫"下午题"或"案例分析"） |
| 题型 | **问答题 + 设计题**：写 SQL、画 ER 图、求候选键、判范式、设计备份方案…… |
| 满分与及格线 | 满分 **75 分**，**45 分及格**；必须与上午"基础知识"**同一次同时过线**，一科挂全作废 |
| 考试形式 | **机考**，全部在电脑上打字作答（设计题可用绘图工具或文字描述） |
| 大题数量 | 近年多为 **4~5 道必答大题**（每道大题再拆成若干小问；**具体以当次试卷为准**） |
| 大题分值感觉 | 通常每道大题 15 分上下（5 道题）或 15~20 分（4 道题） |

### 机考连考机制：下午的时间是从上午"省"出来的

⚠️【必考认知】现在的考试是**两科连考、分批进行**，这直接决定了你的时间策略：

- 基础知识与应用技术**连考**，两科**总作答时长 240 分钟**；
- 基础知识**最短 90 分钟、最长 120 分钟**，交卷后**自动进入**应用技术；
- 所以应用技术实际能分到 **120~150 分钟**：上午 90 分钟就交卷，下午有 **150 分钟**；上午磨满 120 分钟，下午就只剩 120 分钟；
- 具体规则**以当次考试通知为准**，但备考时请按最坏情况（120 分钟也能做完）练，按最好情况（150 分钟）规划。

❗【易错】很多同学以为“下午写满 120 分钟就够用”——错。连考机制下，**你上午浪费的每一分钟都是从下午扣的**。上午卷的目标很明确：90~100 分钟内保质保量交卷，把省下来的时间全部“搬运”到下午。

本套笔记的下午时间策略，一律按 **150 分钟**这个上限来设计。平时练习就直接在电脑记事本里限时写——手写很顺的 SQL，打字时括号引号照样翻车。

## 三、评分真相：老师手里有一张"关键词表"

下午题的评分方式就四个字：**踩点给分**。每道题背后是一张评分点清单，你答案里命中一个点，就得一个点的分，写多不扣分（跑题除外）。由此推出两条铁律：

### 铁律一：名词解释要凑齐"三件套"——定义 + 作用 +（举例）

以"什么是视图"为例，看三个版本的差距：

| 你的答案 | 预估得分 | 点评 |
| --- | --- | --- |
| "视图就是虚的表" | 0~1 分 | 纯大白话，一个关键词没有 |
| "视图是由查询语句定义的虚表，数据库中不实际存储数据" | 约一半分 | 有了"虚表、只存定义"关键词，但缺作用 |
| "视图是从一个或多个基本表（或视图）上通过 SELECT 查询定义的**虚表**，数据库中**只保存其定义而不保存数据**；作用是**简化用户操作**、提供一定的**逻辑数据独立性**，并能作**安全性保护**手段（对不同用户开放不同视图）；例如为财务部建立只包含工资字段的员工视图并只授权给该部门" | 满分 | 定义+作用+例子，三件套齐了 |

### 铁律二：判断题必须"结论 + 理由"，理由要指认"是哪种依赖 / 违反了什么"

以"判断某关系模式是否满足 3NF"为例：

| 你的答案 | 预估得分 | 点评 |
| --- | --- | --- |
| "不满足 3NF" | 1 分 | 只有结论，理由分全丢 |
| "不满足 3NF，因为存在非主属性对候选键的**传递函数依赖**" | 满分 | 结论 + 指认依赖类型 |
| "不满足 3NF：候选键为学号，系名传递函数依赖于学号（学号→系号→系名），而系号、系名均为非主属性" | 满分且漂亮 | 结论 + 指认依赖 + 写出具体依赖链，阅卷老师想扣都无从下手 |

一句大白话总结：**判卷像法官断案——光喊"有罪"不行，必须指出违反了哪一条。**

### 加餐：题干"设问动词"词典——看清题眼再下笔

题干的动词就是评分点的"说明书"，动词不同，期待的答案形态完全不同：

| 题干动词 | 期待你干什么 | 下笔姿势 |
| --- | --- | --- |
| 指出 / 找出 / 列出 | 点名即可，不必展开 | 名词 + 半句依据，分条写 |
| 说明 / 简述 / 什么是 | 定义 + 作用 | 直接套名词解释三件套 |
| 比较 / 区别 | 抓差异 | 两列对照，每列只写差异关键词 |
| 画出 / 补全 / 完善 | 图示规范 | 矩形/椭圆/菱形各就各位，连线标 1/n/m |
| 写出 / 补全语句 | 完整 SQL | 先骨架后填肉，句尾分号 |
| 判断 / 分析 / 是否 | 结论 + 理由 | 指认"哪种依赖/违反什么协议" |
| 为什么 / 原因 | 原理 + 后果 | "因为……，会导致……" |

口诀：**题眼不对，答案白费；动词怎么说，分数就怎么给。**

### 一道 3 分小问的全流程示范

以一道高频小问为例：**"什么是实体完整性？它由哪种约束实现？"** 完整走一遍流程：

- **第一步 看动词**："什么是"→ 定义+作用，直接套模板一三件套；
- **第二步 调关键词**：主键、唯一、非空；
- **第三步 组织成答案**（2~3 行，关键词前置）：

> 实体完整性是指基本表中**主键的取值必须唯一且不能为空**的约束（定义）。它的作用是**保证每个元组都能被唯一标识**，防止出现无法区分的重复记录（作用）。实体完整性通过 **PRIMARY KEY（主键）约束**实现（落点）。

- **第四步 对照评分点自查**：主键 √、唯一 √、非空 √、唯一标识元组 √、PRIMARY KEY √——五个关键词全在，3 分落袋。

概念本身在 [01 数据库基本概念与体系结构](01-数据库基本概念与体系结构.md)，这里示范的是"怎么把它写成能拿分的答案"——同一套流程可以套到任何名词小问上。

## 五、⚠️万能答题模板（考前直接背这四段）

### 模板一：名词解释

> **「XX 是指……（定义），它的作用是……，例如……」**

套用示范（数据独立性）：

> 数据独立性是指**应用程序与数据的物理结构和逻辑结构相互独立、互不影响**的特性。它的作用是当数据结构改变时，**应用程序不必修改**，从而降低维护成本；它分为物理独立性和逻辑独立性，例如数据库更换存储设备时，应用程序无须任何改动。

踩分关键词：**"应用程序不必修改"**——这句是阅卷老师最想看到的，千万别省。

### 模板二：范式判断

> **「先求出候选键为……，主属性为……；存在（或不存在）非主属性对候选键的（部分/传递）函数依赖……，所以 R 最高属于 XNF。」**

套用示范：

> 先求出候选键为（学号），主属性为（学号）。存在非主属性系名对候选键学号的**传递函数依赖**（学号→系号→系名），故不满足 3NF；不存在非主属性对候选键的部分函数依赖，满足 2NF。所以关系模式 R 最高属于 **2NF**。

配套口诀：**"候选键打底，2NF 查部分，3NF 查传递，BCNF 看决定方。"**（决定方指每个函数依赖的左部是否都包含候选键。）

### 模板三：ER图转关系模式

三步走，一步都不能省：

1. **先判断联系类型**：对每一对实体各问一句"一个 X 对应几个 Y"；
2. **再按规则转换**：`1:1` 并入任意一边 ／ `1:n` 并入 n 端 ／ `m:n` 必须拆成独立关系模式；
3. **最后逐一标主键和外键**：每个模式都要交代"主键是谁、外键是谁、指向谁"。

配套口诀：**"一对一并一边，一对 n 进 n 端，多对 n 单独建，主外键挨个点。"**

### 模板四：SQL 书写规范

三条纪律：**关键字大写、一行一子句、先写框架再填条件。** 考场上先把六行骨架默出来，再逐层往里填肉：

```sql
SELECT   ...        -- ① 要哪些列（含聚合函数结果）
FROM     ...        -- ② 涉及哪几张表
WHERE    ...        -- ③ 行级条件（聚合函数不许进这里！）
GROUP BY ...        -- ④ 按什么分组
HAVING   ...        -- ⑤ 组级条件（聚合条件搬进这里）
ORDER BY ...;       -- ⑥ 排序收尾，别忘了分号
```

先有骨架再填内容的好处：**句子结构分先落袋**——阅卷拆分评分点时，FROM 对了、连接条件对了、GROUP BY 对了，即使细节有瑕疵，结构分也稳拿一半以上。

## 六、❗高频丢分点清单（10 条，考前贴墙版）

| # | 丢分点 | 一句话纠正 |
| --- | --- | --- |
| 1 | **m:n 联系没拆成独立关系模式** | m:n 必须单独建表：属性=两端主键+联系属性，主键=两端主键的组合 |
| 2 | **求候选键忘了验证** | 求出来要过两关：既"能函数决定全部属性"（唯一性），又"去掉任何一个属性都不行"（最小性），口诀"能推全部是合格，缺一不可是候选" |
| 3 | **WHERE 里写聚合函数** | `WHERE AVG(salary)>5000` 直接错——聚合条件必须搬进 HAVING |
| 4 | **名词解释只写大白话** | 白话+关键词双保险："就是虚的表（人话），即由查询定义、只存定义不存数据的虚表（黑话）" |
| 5 | **判断题只给结论不给理由** | 理由要指认具体："存在部分函数依赖"／"违反两段锁协议"／"优先图成环" |
| 6 | **1:n 转换时外键放错端** | 外键永远放 n 端：n 个学生属于 1 个系 → 系号写进学生表 |
| 7 | **建表忘写 FOREIGN KEY … REFERENCES** | 建表语句写完默数一遍"主键、外键、CHECK、非空、唯一、默认"六约束 |
| 8 | **SQL 标点细节翻车** | 每句末尾分号；字符串只用英文单引号；中文输入法的引号、分号、逗号是"隐形杀手" |
| 9 | **授权语句顺序写错** | 固定句式 `GRANT 权限 ON 对象 TO 用户`——TO 后面是"人"，不是表 |
| 10 | **事务判断不写依据** | 判"不可串行化"必须给出冲突操作对或说明优先图有环；判"违反 2PL"要指出哪个事务加锁后又加锁 |

丢分点之外，再送你三个"捡分习惯"：

- **不会的小问也要写**：评分点拆得细，你憋出"外键保证参照完整性"半句话就可能踩到一个点，空着是稳定的 0 分；
- **关键词前置**：先写"黑话"（参照完整性、传递函数依赖），再补大白话解释——阅卷老师扫前半行就能给分；
- **字数克制**：名词解释 2~3 行、判断理由 1~2 行足够。写多不加分，还挤占别题时间。

## 七、案例复习法：近 5 次真题做 2 遍

真题是这个星球上最接近"考什么"的东西，近 5 次的案例真题至少做两遍：

- **第一遍：掐时间写。** 120 分钟内完整作答，不会也硬写——先逼自己体验"考场上答不完"的真实压力；
- **第二遍：对照评分点逐条改。** 把官方/教辅的答案要点抄在旁边，**用红字补上自己漏掉的关键词**，感受"我以为我会了"和"评分点要求我写出来"之间的落差；
