## 14.2 模拟大题题面（改编自历年真题风格）

### 【业务描述】

> 宏达驾校准备开发一套学员管理系统。学员报名时需登记姓名、身份证号、联系电话，并在当期选定一名随车教练；一名教练可以带多名学员，但一名学员在同一培训周期内只跟随一名教练训练。驾校的每辆训练车固定由一名教练负责保管，一名教练也只负责一辆车，需记录车辆的车牌号、品牌型号。驾校每月组织多场考试，每场考试有唯一的考试编号，并安排考试科目（科目二或科目三）、考试日期、考试地点。学员可自主预约参加多场考试，每场考试也允许多名学员同时参加；学员参加完每场考试后，系统要记录该学员本场考试的成绩（0~100 分）。系统还需记录教练的姓名、联系电话和驾龄。此外，系统要支持"按教练统计带教学员数量""按科目统计考试通过情况"，并保证"未报名的学员不能预约考试""学员只能预约本校组织的考试"等规则。

### 【问题】

1. 根据业务描述，找出系统中的实体，并指出各实体之间联系的类型。
2. 实习生小李的初步设计如下，请指出错误并改正：
   ① 将"学员—教练"设计为 m:n 联系，并单独建立"带教"表；
   ② 将"教练—车辆"设计为 1:n 联系（一名教练可负责多辆车）；
   ③ 在"学员"表中增加"考试编号"字段，用于记录学员的考试预约；
   ④ 将"成绩"设计为"考试安排"实体的属性。
3. 将正确的 ER 图转换为关系模式，标注每个模式的主键与外键。
4. 用 SQL 建立各数据表，要求体现主键、外键、非空、唯一、检查、默认值等约束。
5. 用 SQL 完成：① 统计每位教练当前带教的学员人数（未带学员的教练也要显示，人数为 0）；② 统计各考试科目的参考人次与平均分；③ 查询 2026 年 10 月参加科目三考试且成绩不低于 60 分的学员姓名及其教练姓名。
6. 若将学员与教练信息冗余存放在一张表：学员教练表(学号, 姓名, 联系电话, 教练工号, 教练姓名, 教练电话)，函数依赖集 F = {学号→姓名, 学号→联系电话, 学号→教练工号, 教练工号→教练姓名, 教练工号→教练电话}。① 求该模式的候选键；② 判断它最高属于第几范式；③ 将其分解为 3NF。
7. 系统上线前需要设计安全与备份方案：① 用 SQL 完成最小权限授权（教务员可查询与维护学员、参加表，前台只能查看学员公开信息）；② 给出备份策略；③ 说明如何防范 SQL 注入。

## 14.3 逐问精讲（每问：参考答案 + 评分点表）

### 问题①：找实体、定联系（ER 题）

**【参考答案】**

实体（4 个）：**学员、教练、车辆、考试安排**。

| 联系名 | 涉及实体 | 联系类型 | 判断依据（回需求找原句） |
|---|---|---|---|
| 带教 | 学员 — 教练 | **1 : n** | "一名教练可以带多名学员，一名学员只跟随一名教练" |
| 负责 | 教练 — 车辆 | **1 : 1** | "每辆车固定由一名教练负责，一名教练只负责一辆车" |
| 参加 | 学员 — 考试安排 | **m : n**（联系属性：成绩） | "学员可参加多场考试，每场考试多名学员同时参加" |

⚠️【必考】判断联系类型的口诀：**两头各问一句"能配几个"**。学员能报多场考试、一场考试能收多名学员 ⇒ m:n。判断完顺手标注联系的属性（成绩挂在"参加"上），后面第 3 问直接用。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| 实体 | 4 个实体齐全（学员、教练、车辆、考试安排） | 2 |
| 联系 | 三个联系的类型正确（1:n、1:1、m:n） | 4 |
| 细节 | 指出"成绩"是"参加"联系的属性 | 1 |

### 问题②：挑错（ER 图找茬题）

**【参考答案】** 逐条对照业务规则：

| 小李的设计 | 为什么错 | 怎么改 |
|---|---|---|
| ① 学员—教练 m:n | 需求明说"一名学员同一周期只跟随一名教练"，是 1:n，不是 m:n | 改为 1:n 联系，且不必单独建表：把"教练工号"作为外键放进学员表 |
| ② 教练—车辆 1:n | 一名教练只负责一辆车，双向都是 1 ⇒ 是 1:1 | 改为 1:1；车辆表加"教练工号"外键并加 UNIQUE 约束保证一车一教练 |
| ③ 学员表加"考试编号"字段 | 学员与考试安排是 m:n：一个学员要参加多场考试，一个字段只能记一场，存不下 | 必须拆出独立模式：参加(学号, 考试编号, 成绩)，主键为(学号, 考试编号) |
| ④ 成绩是"考试安排"的属性 | 成绩是"某学员参加某场考试"才有的结果；同一场考试不同学员分数不同，考试安排本身没有成绩 | 成绩是**联系"参加"的属性**，应放在"参加"模式中 |

❗【易错】属性该挂哪儿的口诀：**谁身上随时都有这个值，就挂谁**。学员没考试时没有成绩、考试安排没人考时也没有成绩，只有"参加"发生那一刻才产生 ⇒ 挂联系上。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| ① | 指出应为 1:n + "教练工号放入学员表" | 2 |
| ② | 指出应为 1:1 | 1 |
| ③ | 指出 m:n 必须独立成表 + 正确的新模式（含成绩） | 2 |
| ④ | 指出成绩属于联系的属性 | 1 |

### 问题③：ER 图转关系模式（标主键外键）

**【参考答案】**

| 关系模式 | 主键 | 外键 | 用的转换规则 |
|---|---|---|---|
| 学员(学号, 姓名, 身份证号, 联系电话, 教练工号) | 学号 | 教练工号 → 教练(工号) | 1:n 联系并入 n 端（学员表加外键） |
| 教练(工号, 姓名, 联系电话, 驾龄) | 工号 | —— | 实体直接转换为一个模式 |
| 车辆(车牌号, 品牌型号, 工号) | 车牌号 | 工号 → 教练(工号) | 1:1 联系并入任意一方 |
| 考试安排(考试编号, 考试科目, 考试日期, 考试地点) | 考试编号 | —— | 实体直接转换为一个模式 |
| 参加(学号, 考试编号, 成绩) | (学号, 考试编号) | 学号 → 学员(学号)；考试编号 → 考试安排(考试编号) | m:n 联系独立成模式，主键 = 两端实体主键的组合 |

⚠️【必考】ER 转换三规则（口诀）：**1:1 随便并、1:n 并到多那边、m:n 必须单独建**。"参加"模式的联系属性（成绩）就是它的非键属性。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| 模式划分 | 5 个模式划分正确 | 3 |
| 主键 | 各模式主键正确（含"参加"的复合主键） | 2 |
| 外键 | 学员、车辆、参加的外键及指向正确 | 3 |
| 属性落位 | "成绩"落在"参加"模式中 | 1 |

### 问题④：建表 SQL（含全部约束类型）

**【参考答案】**

```sql
-- 教练表：主键 + 非空 + 唯一 + 检查
CREATE TABLE 教练 (
    工号      CHAR(6)      PRIMARY KEY,
    姓名      VARCHAR(20)  NOT NULL,
    联系电话  VARCHAR(15)  UNIQUE,
    驾龄      INT          CHECK (驾龄 >= 0)
);

-- 车辆表：主键 + 外键 + 唯一（UNIQUE 实现 1:1 联系）
CREATE TABLE 车辆 (
    车牌号    VARCHAR(10)  PRIMARY KEY,
    品牌型号  VARCHAR(30)  NOT NULL,
    工号      CHAR(6)      UNIQUE,
    FOREIGN KEY (工号) REFERENCES 教练(工号)
);

-- 学员表：主键 + 自增 + 非空 + 唯一 + 外键
CREATE TABLE 学员 (
    学号      INT          AUTO_INCREMENT PRIMARY KEY,
    姓名      VARCHAR(20)  NOT NULL,
    身份证号  CHAR(18)     NOT NULL UNIQUE,
    联系电话  VARCHAR(15),
    教练工号  CHAR(6)      NOT NULL,
    FOREIGN KEY (教练工号) REFERENCES 教练(工号)
);

-- 考试安排表：主键 + 自增 + 检查 + 默认值
CREATE TABLE 考试安排 (
    考试编号  INT          AUTO_INCREMENT PRIMARY KEY,
    考试科目  VARCHAR(10)  NOT NULL CHECK (考试科目 IN ('科目二', '科目三')),
    考试日期  DATE         NOT NULL,
    考试地点  VARCHAR(50)  NOT NULL DEFAULT '总校考场'
);

-- 参加表：复合主键 + 双外键 + 检查
CREATE TABLE 参加 (
    学号      INT,
    考试编号  INT,
    成绩      DECIMAL(5,1) CHECK (成绩 BETWEEN 0 AND 100),
    PRIMARY KEY (学号, 考试编号),
    FOREIGN KEY (学号) REFERENCES 学员(学号),
    FOREIGN KEY (考试编号) REFERENCES 考试安排(考试编号)
);
```

约束类型盘点（写答案时列这个表，阅卷一目了然）：

| 约束 | 出现在哪张表 | 对应完整性类别 |
|---|---|---|
| PRIMARY KEY | 各表 | 实体完整性 |
| FOREIGN KEY … REFERENCES | 车辆、学员、参加 | 参照完整性 |
| NOT NULL / UNIQUE / CHECK / DEFAULT | 各表 | 用户定义完整性 |
| AUTO_INCREMENT | 学员、考试安排 | MySQL 自增特性 |

❗【易错】"未报名学员不能预约考试""学员只能预约本校考试"这两条业务规则，靠"参加"表的两个外键**天然实现**——外键约束保证参加表里的学号必须是已报名学员、考试编号必须是本校考试。作答时点破这一句，就是得分点。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| 基本结构 | 5 张表齐全，列名、类型合理 | 2 |
| 实体完整性 | PRIMARY KEY（含复合主键） | 2 |
| 参照完整性 | 3 处 FOREIGN KEY … REFERENCES | 2 |
| 用户定义完整性 | NOT NULL / UNIQUE / CHECK / DEFAULT 至少各出现一次 | 3 |
| 业务规则 | 点破"外键实现未报名不能预约" | 1 |

### 问题⑤：查询 SQL（多表连接 + 分组统计）

**【参考答案】**

```sql
-- ① 每位教练带教学员人数（没带学员的教练也要出现，人数为 0）
SELECT j.姓名 AS 教练姓名, COUNT(s.学号) AS 学员人数
FROM 教练 j
LEFT JOIN 学员 s ON s.教练工号 = j.工号
GROUP BY j.工号, j.姓名;

-- ② 各考试科目的参考人次与平均分
SELECT k.考试科目, COUNT(*) AS 参考人次, AVG(c.成绩) AS 平均分
FROM 参加 c
JOIN 考试安排 k ON c.考试编号 = k.考试编号
GROUP BY k.考试科目;

-- ③ 2026 年 10 月科目三及格的学员及其教练
SELECT s.姓名 AS 学员姓名, j.姓名 AS 教练姓名
FROM 学员 s
JOIN 教练 j     ON s.教练工号 = j.工号
JOIN 参加 c     ON s.学号 = c.学号
JOIN 考试安排 k ON c.考试编号 = k.考试编号
WHERE k.考试科目 = '科目三'
  AND c.成绩 >= 60
  AND k.考试日期 BETWEEN '2026-10-01' AND '2026-10-31';
```

❗【易错】①必须用 **LEFT JOIN**：普通 JOIN 会把没带学员的教练"吞掉"，人数为 0 就不见了；GROUP BY 里写 j.工号 而不是只写姓名（防同名教练）。③注意连接条件必须逐个写全（4 张表 3 个 ON），漏一个就是笛卡尔积。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| ① | LEFT JOIN；GROUP BY 与 COUNT 配对；0 也显示 | 3 |
| ② | 连接条件；COUNT(*) 与 AVG(成绩)；GROUP BY 考试科目 | 3 |
| ③ | 三个连接条件齐全；WHERE 三条件齐全 | 4 |

### 问题⑥：范式判断与 3NF 分解

**【参考答案】**

① 用候选键四步法（原理见 [12 候选键与范式分解](12-案例-候选键与范式分解.md)）：

| 属性 | 当过左部 | 当过右部 | 归类 | 影响 |
|---|---|---|---|---|
| 学号 | ✓（三条依赖） | ✗ | L类 | **必在候选键** |
| 姓名、联系电话 | ✗ | ✓ | R类 | 排除 |
| 教练工号 | ✓（教练工号→教练姓名） | ✓（学号→教练工号） | LR类 | 待验证 |
| 教练姓名、教练电话 | ✗ | ✓ | R类 | 排除 |

底座 {学号}，求闭包：学号⁺ = {学号} →学号→姓名、联系电话、教练工号→ {学号,姓名,联系电话,教练工号} →教练工号→教练姓名、教练电话→ **全部属性** ⇒ **候选键 = 学号**（唯一）。

② 范式判断：
- 主属性：{学号}；非主属性：其余 5 个
- 候选键为单属性 ⇒ 无部分函数依赖 ⇒ 满足 2NF
- 存在 学号→教练工号、教练工号→教练姓名，且教练工号↛学号 ⇒ 非主属性"教练姓名"**传递函数依赖**于候选键 ⇒ 不满足 3NF
- 结论：**最高属于 2NF**

③ 合成法分解到 3NF：
- F 已是最小函数依赖集（逐条检查：删任一条后，相应左部闭包推不出右部；无多属性左部）
- 每个依赖建一个模式，再把**左部相同**的模式合并：
  - 学号作左部的三条合并 → R1(学号, 姓名, 联系电话, 教练工号)
  - 教练工号作左部的两条合并 → R2(教练工号, 教练姓名, 教练电话)
- 候选键"学号" ⊆ R1 ✓ 不用补模式
- 结果：**学员(学号,姓名,联系电话,教练工号)、教练(教练工号,教练姓名,教练电话)**，均为 3NF、保持函数依赖、无损连接；R1 主键学号、外键教练工号；R2 主键教练工号

❗【易错】这正是问题③里"学员表、教练表分开建"的原因——把两张表冗余合成一张，必然栽在"传递依赖"上。案例题常这样前后呼应，发现第⑥问的分解结果就是第③问的正确设计时，说明你整道题都通了。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| ① | 属性归类；学号⁺ 逐步展开；候选键 = 学号 | 2 |
| ② | 主属性/非主属性；"传递函数依赖"四字；结论 2NF | 3 |
| ③ | 合成/分解出两个模式；主外键标注；保持依赖与无损说明 | 4 |

### 问题⑦：安全与备份方案设计

**【参考答案】**

① 最小权限授权 + 视图隔离：

```sql
-- 教务员：可查询、可维护学员与参加表，教练表只读
CREATE USER 'jw_admin'@'%' IDENTIFIED BY '示例强密码Jw#2026';
GRANT SELECT, INSERT, UPDATE, DELETE ON 驾校库.学员 TO 'jw_admin'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON 驾校库.参加 TO 'jw_admin'@'%';
GRANT SELECT ON 驾校库.教练 TO 'jw_admin'@'%';

-- 前台：只看学员公开信息（身份证号、联系电话被视图挡住）
CREATE VIEW v_学员公开信息 AS
SELECT 学号, 姓名, 教练工号 FROM 学员;
GRANT SELECT ON 驾校库.v_学员公开信息 TO 'front_desk'@'%';
```

② 备份策略（四点，标准答法）：
- **全量**：每周日凌晨用 `mysqldump --single-transaction` 做全库逻辑备份，备份期间业务不停；
- **增量**：开启 binlog，日常靠 binlog 记录增量；恢复 = 最近一次全备 + binlog 重放到故障时刻；
- **保存**：备份文件异机（异地）保存，防止机房级故障"连锅端"；
- **演练**：定期做恢复演练验证可用性；有条件再部署主从复制做热备（注意：主从复制是**可用性**手段，不能替代备份）。

③ 防范 SQL 注入（三点，标准答法）：
- 应用层一律使用**预编译/参数化查询**（占位符 ?），严禁用字符串拼接构造 SQL；
- 数据库账号**最小权限**：Web 使用的账号不授予 FILE、DROP、GRANT 等高危权限；
- 对输入做类型/白名单校验；报错信息不直接回显给前端，防止探测表结构。

**评分点表**：

| 考查点 | 阅卷找什么 | 示意分值 |
|---|---|---|
| ① | GRANT 授权对象与权限正确；REVOKE/最小权限意识；用视图隔离敏感字段 | 3 |
| ② | 全量 + binlog 增量；恢复方法（全备 + binlog 重放）；异地保存/演练 | 3 |
| ③ | 参数化/预编译；最小权限；输入校验（任答两条即可） | 2 |

## 14.4 ⚠️考前必背清单（压轴，全站收尾）

### 14.4.2 案例必背模板 10 句（标准句式，照抄就能得分）

1. **事务定义**：事务是用户定义的一个数据库操作序列，这些操作要么全做、要么全不做，是不可分割的工作单位。
2. **候选键作答**：本关系模式的候选键为____，主属性为____，非主属性为____。
3. **判 1NF**：由于非主属性____部分函数依赖于候选键____，故不满足 2NF，最高属于 1NF。
4. **判 2NF**：由于存在 A→B、B→C 且 B 不能决定 A，非主属性 C 传递函数依赖于候选键 A，故不满足 3NF，最高属于 2NF。
5. **无损作答**：用 Chase 表格法检验，最终表格中出现一行全 ✓，故该分解具有无损连接性。（二目分解可口诀作答）
6. **依赖保持作答**：分解后各模式上函数依赖投影的并集能逻辑蕴含原函数依赖集 F，故该分解保持函数依赖。
7. **封锁协议作答**：当前采用__级封锁协议，因__（缺陷）导致__问题；改用__级封锁协议（加锁规则：__）即可防止。
8. **2PL 作答**：两段锁协议规定事务分为扩展、收缩两个阶段，扩展阶段只加锁、收缩阶段只释放锁；遵守 2PL 的并发调度一定是可串行化的。
9. **可串行化作答**：构造优先图，图中存在环，故该调度不可串行化；图中无环，故该调度可串行化，等价于串行调度 T_→T_。
10. **恢复作答**：利用 redo 日志重做已提交事务（前滚），利用 undo 日志回滚未完成事务（后滚），并配合检查点缩短恢复时间。
